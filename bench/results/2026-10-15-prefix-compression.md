# 块内 key 前缀压缩的前后对比

2026-10-15。要回答的问题：数据块里的 key 改为只存与块的第一个 key 不同的部分之后，SST 小了多少，读写的吞吐有没有变化。之前的一版是 [2026-10-14 Bloom filter 的前后对比](2026-10-14-bloom-filter.md) 里的"之后"。

- 机器：Apple M5（Mac17,2），10 个逻辑 CPU，32 GB 内存，macOS 26.6.2，**使用电池**；内置 SSD，APFS。
- 代码状态："之前"是加了 Bloom filter、块格式未改的一版（提交 1bdf778 之上的工作区，把 `block.rs`、`block/builder.rs`、`block/iterator.rs` 换回 1bdf778 的内容）；"之后"是加了前缀压缩的工作区，即与本记录一起提交的那一版。
- 两版**交替运行**：每一轮依次跑"之前"与"之后"的三组配置，共三轮，下表取中位数。
- 同一配置三次之间的吞吐浮动较大，多数在 10%～28% 之间（电池供电）。下面的吞吐差距都在浮动之内，不作为结论；文件大小与计数器是确定的，三次完全相同。

重跑方式（在 `lsm/` 下）：

```sh
# A：30 万条乱序写入，33 个 SST。--block-cache-mb 取 0 与 64。
cargo run --release -p lsm-bench -- --target engine --num 300000 --memtable-mb 1 --block-cache-mb 0 --workloads fillrandom,readrandom,readmissing,seekrandom
# C：100 万条，先 fillrandom 再 overwrite，55 个 SST，块缓存 64 MB。
cargo run --release -p lsm-bench -- --target engine --memtable-mb 4 --block-cache-mb 64
```

## 文件大小：小了 8%，与估算一致

| 组 | 负载 | 写出的 SST 字节（之前 → 之后） | 变化 | 写放大 |
| --- | --- | --- | ---: | --- |
| A | fillrandom | 37,148,397 → 34,201,874 | −7.9% | 1.07 → 0.98 |
| C | fillrandom | 121,568,229 → 111,862,529 | −8.0% | 1.05 → 0.96 |
| C | overwrite | 123,856,651 → 113,971,532 | −8.0% | 1.07 → 0.98 |

**估算。** 基准的 key 是 16 位十进制数、前面补 0；30 万个 key 的编号不超过 60 万，前 10 个字符都是 `0`。一个块约 33 条，按同样的写法模拟，每个 key 与块的第一个 key 平均共有 12.1 字节。每条记录省下约 12 字节，又多了 2 字节的"共有前缀长度"，净省约 10 字节；原来一条记录连同偏移是 122 字节，所以约 8%。实测的 7.9%～8.0% 与此相符。

**写放大低于 1。** 写放大的分母是用户交给引擎的字节（key 加 value，每条 116 字节），分子是写到磁盘的字节。压缩之后一条记录在文件里约 112 字节（key 的剩余部分约 4 字节、value 100 字节，加上 3 个长度字段与偏移共 8 字节），摊上索引、filter、footer 约 114 字节，仍比 116 少。没有 compaction 与 WAL 时这是正常的；有了它们，写放大会回到 1 以上。

**块数也少了。** A 组缓存 64 MB 时，全部数据块放进缓存：之前 9042 块、34.7 MB，之后 8316 块、31.9 MB。每个块仍是约 4 KB，装的记录多了。C 组的缓存只放得下约四分之一的数据，每次 readrandom 从文件读的块从 0.79 降到 0.75，readmissing 从 0.37 降到 0.36，与"同样的缓存多放了约 8% 的记录"一致。

## 吞吐：变化在浮动之内

吞吐的单位是万次每秒。

| 组 | 负载 | 之前 | 之后 |
| --- | --- | ---: | ---: |
| A，不用缓存 | fillrandom | 384 | 400 |
| A，不用缓存 | readrandom | 50.9 | 49.0 |
| A，不用缓存 | readmissing | 97.5 | 96.4 |
| A，不用缓存 | seekrandom | 1.67 | 1.69 |
| A，缓存 64 MB | readrandom | 63.3 | 64.6 |
| A，缓存 64 MB | readmissing | 94.7 | 104 |
| A，缓存 64 MB | seekrandom | 2.21 | 2.46 |
| C，缓存 64 MB | readrandom | 23.3 | 22.3 |
| C，缓存 64 MB | readmissing | 32.0 | 30.9 |
| C，缓存 64 MB | seekrandom | 0.53 | 0.53 |

- **还原 key 的开销没有显出来。** 压缩之后，游标每走一步要把"第一个 key 的前缀"和"剩余部分"拼进自己的缓冲区，二分查找的每一步也要拼一次。对 16 字节的 key 这只是一次很短的复制，缓冲区反复使用、不再分配内存；扫描与点查的吞吐没有超出浮动的变化。
- **省下的空间没有变成速度。** 数据都在页缓存里，读一个块的代价主要是系统调用与解码，块里多装 8% 的记录不会让它明显变快。数据大于内存、块缓存放不下全部数据时，同样的缓存能多装 8% 的记录、读同样多的记录少读 8% 的块，收益才会出现。
- 本次的绝对吞吐比 2026-10-14 那次低一到两成，两次都用电池，但机器状态不同；只比较本记录里交替运行的两版。

## 没有验证的地方

- 电池供电，吞吐的浮动大，前后差距小于浮动，不能下结论说压缩之后变快或变慢。
- 只测了 16 字节、前缀高度重复的 key。key 是随机字节（如哈希值）时，相邻 key 几乎没有共有前缀，每条记录反而多 2 字节。
- 没有测数据大于内存的情况。

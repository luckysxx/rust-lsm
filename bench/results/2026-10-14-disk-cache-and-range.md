# SST 落盘之后：块缓存与按 key 范围跳过文件

2026-10-14。要回答的问题：冻结的表写成 SST 之后，读的代价变成多少；块缓存的容量与按 key 范围跳过文件各带来多少变化；与 2026-10-10 冻结的表还留在内存里时相比如何。

- 机器：Apple M5（Mac17,2），10 个逻辑 CPU，32 GB 内存，macOS 26.6.2，接电源；内置 SSD，APFS。
- 代码状态：提交 cee7497 之上的工作区，即与本记录一起提交的那一版。引擎：memtable 写满冻结，后台线程写成 L0 的 SST（同步文件与目录），没有 compaction，L0 只增不减；点查与扫描用每个 SST 的首末 key 跳过范围之外的文件；读块先查块缓存（moka，按块在内存里的大小计容量），块大小 4 KB，不压缩。
- 单线程。每个配置运行 3 次，下表取中位数；同一配置三次之间的浮动除注明的以外在 5% 以内。
- 每段负载计时结束后，驱动程序等冻结的表全部写成 SST，再读计数器、开始下一段。可写的那张 memtable 不会被冻结，里面留着最后不到一张表的数据，所以有约 1%～3% 的点查在内存里就查到了。

重跑方式（在 `lsm/` 下）：

```sh
# A：块缓存的容量。乱序写入，文件的 key 范围互相重叠。
cargo run --release -p lsm-bench -- --target engine --num 300000 --memtable-mb 1 --block-cache-mb 0 --workloads fillrandom,readrandom,readmissing,seekrandom
# 同上，--block-cache-mb 换成 16、64
# B：按 key 范围跳过文件。顺序写入，文件的 key 范围互不重叠。
cargo run --release -p lsm-bench -- --target engine --num 300000 --memtable-mb 1 --block-cache-mb 0 --workloads fillseq,readrandom,readmissing,seekrandom
# 同上，--block-cache-mb 换成 64
# C：与 2026-10-10 相同的参数。
cargo run --release -p lsm-bench -- --target engine --memtable-mb 4 --block-cache-mb 64
```

**读文件基本都命中了操作系统的页缓存。** 数据刚写完，A、B 组的文件共约 37 MB，C 组约 240 MB，都远小于 32 GB 内存，测试前没有清空页缓存。所以下面"从文件读一个块"的代价是一次 `pread` 系统调用、复制、分配与解码，不含 SSD 的访问延迟。数据远大于内存时，没有命中块缓存的代价会高得多。

## A：块缓存的容量

30 万条，memtable 上限 1 MB，乱序写入，结束时 L0 有 33 个 SST，共约 37 MB；每个文件的 key 范围都几乎覆盖全部 key，范围检查排除不了任何文件。

| 块缓存 | readrandom（万次/秒） | readmissing | seekrandom | 每次点查进入的 SST（readrandom / readmissing） | 每次点查从文件读的块 |
| --- | ---: | ---: | ---: | --- | --- |
| 0 | 5.85 | 2.93 | 1.91 | 16.9 / 33.0 | 16.9 / 33.0 |
| 16 MB（约数据的 45%） | 6.77 | 2.90 | 1.87 | 16.9 / 33.0 | 6.3 / 17.2 |
| 64 MB（全部放得下） | 16.3 | 8.27 | 3.50 | 16.9 / 33.0 | 0.03 / 0.00 |

p99 延迟（微秒），readrandom / readmissing / seekrandom：缓存 0 时 39 / 48 / 70，16 MB 时 48 / 63 / 86，64 MB 时 16 / 21 / 40。

- **点查要看一半的文件，查不存在的 key 要看全部。** 33 个文件范围都重叠：查到的 key 平均在第 17 个文件里找到，不存在的 key 要把 33 个都看完。这是没有 compaction、没有 Bloom filter 时的读放大。
- **数据全部放进缓存时，点查快 2.8 倍。** 不用缓存时，查不存在的 key 每次约 34 微秒，摊到每个文件约 1 微秒；全部命中缓存时每个文件约 0.36 微秒。省下的约 0.65 微秒就是"从页缓存读一个块并解码"的代价。
- **缓存只放得下一半时，几乎没有收益。** 16 MB 时从文件读的块少了一半到三分之二，吞吐却只多了 16%（readrandom），readmissing 与扫描没有变化，p99 还变差了。推测是缓存满了之后，每次没命中都要放进缓存并触发淘汰，这部分开销抵消了命中省下的时间；没有用剖析工具确认。数据只在页缓存里时，没命中的代价本来就小，块缓存的价值要在数据大于内存、没命中真正读 SSD 时才显出来。

## B：按 key 范围跳过文件

同样 30 万条，改为按 key 从小到大写入（`fillseq`）。每次 flush 写出的文件 key 范围互不重叠，结束时同样是 33 个 SST。

| 写入顺序 | 块缓存 | readrandom（万次/秒） | readmissing | seekrandom | 每次点查进入的 SST |
| --- | --- | ---: | ---: | ---: | ---: |
| 乱序（A 组） | 0 | 5.85 | 2.93 | 1.91 | 16.9 / 33.0 |
| 顺序 | 0 | 82.8 | 84.9 | 3.55 | 0.99 / 0.99 |
| 乱序（A 组） | 64 MB | 16.3 | 8.27 | 3.50 | 16.9 / 33.0 |
| 顺序 | 64 MB | 151 | 169 | 6.39 | 0.99 / 0.99 |

- **文件范围不重叠时，每次点查只进入一个文件。** 不用缓存时 readrandom 快 14 倍，readmissing 快 29 倍：不存在的 key 也只落在一个文件的范围里，读一个块就能确定没有。p99 都在 2 微秒左右。
- **compaction 之后的层就是这个样子。** 乱序写入时 L0 的文件范围必然重叠；compaction 把它们整理成范围互不重叠的层之后，点查就能得到接近 B 组的效果。
- **扫描只快了不到一倍。** 驱动程序的扫描没有上界（从起点读 100 条为止），范围检查只能排除整个落在起点之前的文件，起点之后的文件仍然各建一个游标、各读一个块。带上界的扫描能排除更多。
- 顺序写入本身也更快：`fillseq` 约 774 万次每秒，乱序约 443 万。跳表的插入位置总在末尾附近，访问的节点都在 CPU 缓存里。

## C：与 2026-10-10 对照

参数与 [2026-10-10](2026-10-10-engine-and-scan.md) 中"memtable 上限 4 MB"那一组相同：100 万条，先 `fillrandom` 再 `overwrite`。那时冻结的表不落盘，结束时内存里有 56 张表；现在它们写成了 55 个 SST，块缓存 64 MB，约放得下数据的四分之一。

| | fillrandom（万次/秒） | overwrite | readrandom | readmissing | seekrandom |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2026-10-10，56 张冻结的表在内存里 | 386 | 376 | 4.2 | 1.6 | 0.62 |
| 本次，55 个 SST | 332 | 318 | 2.6 | 0.93 | 0.69 |

本次的计数器：写放大 1.04（fillrandom）与 1.06（overwrite）；readrandom 每次进入 22.8 个 SST、从文件读 12.8 个块，readmissing 每次进入 55 个、读 39 个。

- **点查慢了约四成。** 在 SST 里查一个 key 要找块、读块（或查缓存）、在块内二分，比在跳表里查一次贵；缓存只放得下四分之一，多数块要从文件读。
- **扫描反而略快。** SST 的游标在一个解码好的块里顺着走，memtable 的游标每前进一步都要重新定位（L03 的选择）。原因是推测，没有剖析确认；seekrandom 三次之间浮动 13%，差距在浮动之内，不能当作结论。
- **写入的吞吐略低，而且没有算上落盘。** 写入只进 memtable，计时结束后又等了 0.1～0.15 秒才全部落盘（A 组写入本身只用 0.08 秒）。没有写入停顿时，写入的吞吐衡量的是内存，不是磁盘；算上等待，A 组的写入约为每秒 140 万次。
- **写放大 1.04～1.06。** 目前只有 flush 一处写磁盘，多出来的是编码开销：每条记录两个 2 字节的长度和 2 字节的偏移，约 6 字节，加上索引与文件尾。overwrite 这段把每个 key 又写了一遍，旧值留在文件里，空间放大约为 2，要等 compaction 清理。
- 两次的电源状态不同（那次使用电池，这次接电源），对比只看量级。

## 没有验证的地方

- 16 MB 缓存几乎没有收益的原因（放入与淘汰的开销）没有用剖析工具确认。
- 没有清空页缓存，也没有在数据大于内存的规模下测试，SSD 的真实读取延迟没有进入这组数字。
- 只有单线程；块缓存在多个线程同时读时的争用没有测。

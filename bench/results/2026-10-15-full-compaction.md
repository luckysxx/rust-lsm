# 全量 compaction 的前后对比

2026-10-15。要回答的问题：把 L0 的全部文件合并成一层范围互不重叠的 L1 之后，点查与扫描快了多少；合并本身花多久、写了多少字节，写放大与空间放大怎样变化。

- 机器：Apple M5（Mac17,2），10 个逻辑 CPU，32 GB 内存，macOS 26.6.2，**使用电池**；内置 SSD，APFS。
- 代码状态：提交 8fcde10 之上加了 compaction 的工作区，即与本记录一起提交的那一版（L09：L1、串接游标、`force_full_compaction`，基准驱动的 `compact` 负载与"结束时的 SST"三列）。
- 前后对比在**同一次运行**里完成：先写入、读一遍，执行 `compact`，再读一遍。每个配置运行 3 次，下表取中位数；同一配置三次之间的浮动注明在各组下面。
- 引擎没有自动的 compaction，只在执行 `compact` 负载时合并一次。

重跑方式（在仓库根目录下）：

```sh
# A：30 万条乱序写入，33 个 L0 文件。--block-cache-mb 取 0 与 64。
cargo run --release -p lsm-bench -- --target engine --num 300000 --memtable-mb 1 --block-cache-mb 0 --workloads fillrandom,readrandom,readmissing,seekrandom,compact,readrandom,readmissing,seekrandom
# C：100 万条，先 fillrandom 再 overwrite，55 个 L0 文件，块缓存 64 MB。
cargo run --release -p lsm-bench -- --target engine --memtable-mb 4 --block-cache-mb 64 --workloads fillrandom,overwrite,readrandom,readmissing,seekrandom,compact,readrandom,readmissing,seekrandom
```

## 读：每次点查只进入一个文件，扫描快了一个数量级

吞吐的单位是万次每秒。"之前"是 L0 有 33（A）或 55（C）个范围重叠的文件，"之后"是同样的数据合并成 L1。

| 组 | 负载 | 之前 | 之后 | 倍数 | 每次点查进入的 SST（之前 → 之后） |
| --- | --- | ---: | ---: | ---: | --- |
| A，不用缓存 | readrandom | 57.3 | 71.7 | 1.25 | 1.13 → 0.99 |
| A，不用缓存 | readmissing | 109 | 518 | 4.8 | 0.29 → 0.01 |
| A，不用缓存 | seekrandom | 1.95 | 16.4 | 8.4 | — |
| A，缓存 64 MB | readrandom | 84.5 | 110 | 1.30 | 1.13 → 0.99 |
| A，缓存 64 MB | readmissing | 127 | 534 | 4.2 | 0.29 → 0.01 |
| A，缓存 64 MB | seekrandom | 3.20 | 23.3 | 7.3 | — |
| C，缓存 64 MB | readrandom | 30.0 | 54.3 | 1.8 | 1.21 → 0.99 |
| C，缓存 64 MB | readmissing | 39.9 | 376 | 9.4 | 0.55 → 0.01 |
| C，缓存 64 MB | seekrandom | 0.72 | 13.8 | 19 | — |

A 组不用缓存时，合并之后的 readmissing 与 seekrandom 三次之间浮动约 25%，其余在 13% 以内。

- **扫描受益最大。** 合并之前，一次扫描要在每个范围重叠的文件上各建一个游标、各读一个块，再用堆归并 33 或 55 路；合并之后 L1 是一个串接游标，只打开起点所在的那个文件，顺着读下去。文件越多，差距越大：A 组 7～8 倍，C 组 19 倍。
- **查不存在的 key 快了 4～9 倍。** 有 Bloom filter 时，合并之前每次 readmissing 只进入 0.29 或 0.55 个文件，但仍要对 33 或 55 个文件各做一次范围检查、问一次 filter；合并之后只找到一个候选文件，问一次 filter（误报 1%，所以进入 0.01 个）。剩下的开销几乎只有查 memtable 与算一次哈希，p99 降到 0.3～0.9 微秒。
- **查存在的 key 只快了 25%～80%。** 合并之前 Bloom filter 已经把进入的文件压到 1.13 或 1.21 个，必须读的那一个块省不掉；省下的是对其余文件的检查和少量误报。C 组收益更大，还因为空间减半之后缓存装得下更多数据：每次点查从文件读的块从 0.75 降到 0.41。

## 合并本身：花多久、写了多少

| 组 | 合并前的 SST | 合并后的 SST | 耗时 | 写出的字节 |
| --- | --- | --- | ---: | ---: |
| A | 33 个 L0，34.2 MB | 32 个 L1，33.7 MB | 0.17 s | 33.7 MB |
| C | 55 个 L0，225.8 MB | 27 个 L1，113.1 MB | 0.42 s | 113.1 MB |

- A 组没有覆盖写，合并只是把 33 个范围重叠的文件重新切成 32 个范围不重叠的文件，总大小几乎不变（少了的约 1% 是文件数变少后省下的索引与 filter）。
- C 组每个 key 写过两次，合并丢掉了每个 key 的旧版本，总大小减半。
- 合并在调用它的线程里一次做完，期间读写照常（这次运行里合并时没有其他负载）。

## 写放大与空间放大

| 组 | 用户写入 | 磁盘写入（flush + compaction） | 整次运行的写放大 | 空间放大（合并前 → 合并后） |
| --- | ---: | ---: | ---: | --- |
| A | 34.8 MB | 34.2 + 33.7 MB | 1.95 | 0.98 → 0.97 |
| C | 232.0 MB | 225.8 + 113.1 MB | 1.46 | 1.95 → 0.98 |

空间放大 = 结束时 SST 的总字节 ÷ 全部 key 各一份的大小（key 16 字节加 value 100 字节）。

- **compaction 把数据又写了一遍。** A 组每条数据写了两次（flush 一次、合并一次），写放大从 0.98 变成 1.95。C 组只合并了一次，而写入有两轮，所以摊下来是 1.46。这就是 compaction 用写换读和空间的那笔交换：现在只合并一次，代价是 1 倍；以后自动、反复地合并，每条数据被重写的次数取决于策略（L10～L12）。
- **覆盖写的空间放大从 1.95 降到 0.98。** 合并之前旧版本留在旧文件里，磁盘上存着两份；合并之后只剩最新的一份。小于 1 是因为前缀压缩让每条记录在文件里比 key 加 value 本身还短。
- **删除在这组负载里没有体现。** 基准没有删除负载；有删除时，合并还会丢掉墓碑与被删的值。

## 观察到但没有处理的地方

- **合并读输入时经过块缓存。** 合并按顺序读完所有输入文件，读到的块都放进了缓存，而这些文件合并完就被删除，等于用即将作废的块挤掉了有用的块。RocksDB 为 compaction 的读取关掉放入缓存（`fill_cache = false`）。这次运行里 64 MB 的缓存在合并之后的 readrandom 中很快又被新文件填满，所以没有显出影响；数据大于缓存时值得处理。
- 使用电池；只有单线程；没有测合并与写入同时进行时前台的延迟。
- 合并只做了一次，三种放大在"持续写入、反复合并"下的数值要等 L10～L12 的自动策略。

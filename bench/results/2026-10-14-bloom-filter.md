# Bloom filter 的前后对比

2026-10-14。要回答的问题：给每个 SST 加上 Bloom filter（每个 key 10 位，目标误判率 1%）之后，点查进入的 SST 与读的块少了多少，吞吐与延迟变化多大，代价是什么。之前的数字见 [2026-10-14 块缓存与按 key 范围跳过文件](2026-10-14-disk-cache-and-range.md)，参数相同。

- 机器：Apple M5（Mac17,2），10 个逻辑 CPU，32 GB 内存，macOS 26.6.2，**使用电池**；内置 SSD，APFS。
- 代码状态："之前"是提交 1bdf778（与上一份记录的代码相同，只差文档），"之后"是其上加入 Bloom filter 的工作区，即与本记录一起提交的那一版。两版在同一时段、同样的电源状态下各跑一遍：先把"之前"的四组各跑 3 次，再跑"之后"的。
- 每个配置运行 3 次，下表取中位数。除注明的以外，同一配置三次之间的浮动在 15% 以内。
- 上一份记录是接电源时跑的，本次"之前"的数字与它相差在一到两成以内，量级一致；对比只看本记录里的前后两列。

重跑方式（在 `lsm/` 下）：

```sh
# A：乱序写入，33 个 SST 的 key 范围互相重叠。--block-cache-mb 取 0 与 64。
cargo run --release -p lsm-bench -- --target engine --num 300000 --memtable-mb 1 --block-cache-mb 0 --workloads fillrandom,readrandom,readmissing,seekrandom
# B：顺序写入，33 个 SST 的 key 范围互不重叠。
cargo run --release -p lsm-bench -- --target engine --num 300000 --memtable-mb 1 --block-cache-mb 0 --workloads fillseq,readrandom,readmissing,seekrandom
# C：100 万条，先 fillrandom 再 overwrite，55 个 SST，块缓存约放得下四分之一。
cargo run --release -p lsm-bench -- --target engine --memtable-mb 4 --block-cache-mb 64
```

## 计数器：与预测一致

没有 compaction 时，L0 的 N 个文件范围都重叠。filter 的误判率为 p 时，查一个存在的 key 预计进入 1 + (N − 1)·p 个文件（真正有它的那个，加上误报），查不存在的 key 预计进入 N·p 个。

| 组 | 负载 | 之前进入的 SST | 之后进入的 SST | 之后被 filter 排除的 SST | 之后每次读的块（不用缓存） |
| --- | --- | ---: | ---: | ---: | ---: |
| A（N = 33） | readrandom | 16.9 | 1.13 | 15.8 | 1.13 |
| A | readmissing | 33.0 | 0.29 | 32.7 | 0.29 |
| B（范围不重叠） | readrandom | 0.99 | 0.99 | 0 | 0.99 |
| B | readmissing | 0.99 | 0.01 | 0.99 | 0.01 |
| C（N = 55） | readrandom | 22.8 | 1.21 | 21.6 | 0.79（有缓存） |
| C | readmissing | 55.0 | 0.55 | 54.4 | 0.37（有缓存） |

实测的误判率：A 组 0.29 / 33 ≈ 0.9%，C 组 0.55 / 55 = 1.0%，与目标的 1% 一致。

## 吞吐与延迟

吞吐的单位是万次每秒；p99 的单位是微秒。

| 组 | 负载 | 之前 | 之后 | 倍数 | p99 之前 → 之后 |
| --- | --- | ---: | ---: | ---: | --- |
| A，不用缓存 | readrandom | 6.37 | 57.3 | 9.0 | 34 → 3.8 |
| A，不用缓存 | readmissing | 2.83 | 111 | 39 | 57 → 3.1 |
| A，缓存 64 MB | readrandom | 14.2 | 93.1 | 6.5 | 19 → 3.0 |
| A，缓存 64 MB | readmissing | 7.36 | 137 | 19 | 23 → 2.1 |
| B，不用缓存 | readrandom | 81.6 | 81.5 | 1.0 | 1.7 → 1.8 |
| B，不用缓存 | readmissing | 81.9 | 622 | 7.6 | 1.6 → 0.3 |
| C，缓存 64 MB | readrandom | 2.84 | 32.3 | 11 | 116 → 14 |
| C，缓存 64 MB | readmissing | 1.00 | 42.9 | 43 | 160 → 12 |

写入与扫描在浮动之内没有变化：A 组 fillrandom 427 → 437 万次每秒，B 组 fillseq 773 → 781，C 组 overwrite 320 → 324；seekrandom 在 A 组缓存 64 MB 时 3.33 → 3.31，B 组 3.54 → 3.53。

- **查不存在的 key 几乎不再碰文件。** 33 个文件里平均只有 0.29 个误报，一次 readmissing 从约 35 微秒降到约 0.9 微秒，剩下的主要是查 memtable、算一次哈希、在 33 个 filter 里各查 6 位。
- **查存在的 key 只剩"真正有它的那个文件"。** 之后每次 readrandom 读 1.13 个块，其中 1 个是必须读的。缓存 0 与 64 MB 之间仍差 1.6 倍，就是这一个块从页缓存读出并解码的代价，Bloom filter 帮不上。
- **范围已经互不重叠时（B 组），存在的 key 没有变化。** 范围检查已经把候选缩到真正有它的那一个文件，filter 回答"可能有"，什么也没省。不存在的 key 则从"读一个块才知道没有"变成"不读块"，快了 7.6 倍。compaction 之后的每一层都是这种情况：一个 key 在每层最多一个候选文件，filter 省掉的是"候选文件里其实没有"的那一次读。
- **扫描用不上 filter。** filter 只能回答某一个 key 在不在，扫描的结果不变在意料之中。

## 代价

- **文件变大约 1%。** A 组 33 个 SST 一共多了 373,197 字节，每个文件约 11.3 KB：约 9000 个 key × 10 位 = 11.25 KB，加 1 字节的 k 和 footer 多出的 8 字节。写放大从 1.06 变为 1.07。
- **内存。** 打开文件时 filter 整个读进内存并常驻：A 组 33 个文件约 370 KB；C 组 55 个文件约 2.5 MB（两段负载共写进 200 万条记录，被覆盖的旧值仍在文件里，各占 filter 的位）。每个 key 约 1.25 字节，数据大到上亿条时需要另想办法（RocksDB 把 filter 切块放进块缓存）。
- **写入时每个 key 多算一次哈希。** 吞吐在浮动之内没有变化，没有单独剖析这一项。

## 没有验证的地方

- 使用电池；两版是先后跑的，没有交替运行。A 组不用缓存时"之后"的 seekrandom 三次之间浮动 29%（其中一次最大延迟约 8 毫秒），与 Bloom filter 无关（扫描不经过它），推测是电源管理带来的抖动。
- 与上一份记录一样，文件都在页缓存里，没有测数据大于内存、没命中真正读 SSD 的情况。那种情况下每次误报都是一次磁盘读，filter 的收益会更大。
- 只有单线程；没有测每个 key 的位数（误判率）取其他值时的权衡。

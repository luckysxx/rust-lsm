# manifest：吞吐与放大基本不变，写入的最大延迟从几十微秒变成几毫秒

2026-10-20。要回答的问题：每次 flush 与合并换状态多一次 fsync（追加 manifest 记录），而且是在 `state_lock` 里做的，对写入的吞吐、延迟、写完之后等后台的时间、读与写放大各有多大影响。

- 机器：Apple M5（Mac17,2），10 个逻辑 CPU，32 GB 内存，macOS 26.6.2，**接电源**；内置 SSD，APFS。前几次记录是电池供电，数字不能与它们直接比。
- 代码状态：
  - 之前：提交 611eb2b（L12 之后，含 leveled 的 L0 不跳过有数据的上层的修复），没有 manifest。
  - 之后：同一提交之上加了 L13 的工作区，即与本记录一起提交的那一版（`manifest` 模块；flush 与合并在 `state_lock` 里追加并同步一条记录；打开时重放）。基准驱动的报告多了"MANIFEST 有几条记录"，负载与计时没有变。
- 对照对象：同一台机器、同一时段、交替运行的之前与之后两版，参数完全相同。
- 每个配置每版运行 3 次，下表取中位数，方括号里是三次的最小与最大值。

重跑方式（在 `lsm/` 下，同一组参数分别用两版的二进制运行）：

```sh
cargo run --release -p lsm-bench -- --target engine --memtable-mb 4 --block-cache-mb 64 --workloads fillrandom,overwrite,readrandom,readmissing,seekrandom \
  --compaction simple --l0-trigger 2 --size-ratio 200 --max-levels 4          # S
# T8：--compaction tiered --num-tiers 8
# L：--compaction leveled --l0-trigger 2 --level-multiplier 10 --base-level-mb 8 --max-levels 4
# Lseq：L 的参数，--workloads fillseq
# N1：--memtable-mb 1 --workloads fillrandom --compaction none（只有 flush，记录最多、写入最快）
```

macOS 上 Rust 的 `File::sync_all` 是 `fcntl(F_FULLFSYNC)`：要求磁盘把缓存也写下去。在这台机器上对一个小文件追加 100 字节再 `F_FULLFSYNC`，50 次的中位数 3.0 毫秒、最多 6.4 毫秒。

## 写入：吞吐差一点，最大延迟高了约一百倍

| 组 | 写入吞吐（万次/秒），之前 → 之后 | 最大延迟（µs），之前 → 之后 | p99.9（µs），之前 → 之后 | MANIFEST 的记录 |
| --- | --- | --- | --- | ---: |
| S 简单分层 | 308 [305-314] → 315 [285-316] | 65 [43-107] → 5550 [4300-6000] | 2.1 → 1.5 | 75～76 条，8 KB |
| T8 tiered | 348 [317-355] → 329 [311-337] | 43 [33-98] → 3840 [3030-5040] | 1.7 → 1.7 | 62～64 条，6 KB |
| L leveled | 328 [279-345] → 309 [293-310] | 41 [26-130] → 7520 [6640-11800] | 1.7 → 2.0 | 121～124 条，12 KB |
| Lseq leveled，顺序写入 | 698 [685-722] → 611 [585-630] | 40 [19-44] → 8070 [6110-9210] | 1.2 → 1.2 | 57～59 条，5 KB |
| N1 不合并，memtable 1 MB | 435 [423-435] → 307 [287-312] | 42 [22-56] → 5960 [4030-6740] | 1.4 → 1.4 | 111 条，9 KB |

S、T8、L 是 fillrandom 一段，Lseq 是 fillseq，N1 是 fillrandom。

- **最大延迟从几十微秒变成几毫秒，正好是一两次 `F_FULLFSYNC`。** 写入写满 memtable 时要冻结，冻结要拿 `state_lock`；这时 flush 或合并正拿着它追加 manifest 并同步，写入就要等这次 fsync 做完。p99.9 不变：一百万次写入里只有几十次冻结，碰上 fsync 的更少，只影响最慢的那几次。
- **吞吐：S、T8、L 在浮动附近（差 0～6%），Lseq 低一成多，N1 低三成。** 冻结越频繁、写入本身越快，等 fsync 的时间占的比例越大。N1 的 memtable 只有 1 MB、不合并，写入每秒 430 万次，整段只要约 0.23 秒，期间有一百多次冻结。Lseq 是顺序写入，leveled 几乎全是 trivial move：原来挪动只改内存，现在每次挪动也要一次 fsync。
- **确认原因的对照**：把 `Manifest::append` 里的同步临时去掉（只写、不同步），N1 三次的吞吐是 385、443、430 万次/秒，最大延迟 94、38、64 微秒，回到之前的水平。所以变化全来自这次 fsync，而不是编码、写文件或换状态的方式。这个改动没有保留。

## 写完之后等后台：每条记录多约 3 毫秒

| 组 | fillrandom（或 fillseq）之后等后台 (s)，之前 → 之后 | overwrite 之后 (s)，之前 → 之后 |
| --- | --- | --- |
| S | 1.11 → 1.28 | 1.01 → 1.07 |
| T8 | 0.36 → 0.45 | 0.42 → 0.44 |
| L | 0.92 → 1.15 | 1.13 → 1.45 |
| Lseq | 0.23 → 0.40 | — |
| N1 | 0.49 → 0.83 | — |

后台每换一次状态多一次 fsync，多出来的时间大约是"记录数 × 3 毫秒"：N1 是 111 × 3 ≈ 0.33 秒，实际多了 0.34 秒；Lseq 是 58 × 3 ≈ 0.17 秒，实际多了 0.17 秒。

## 读与写放大：不变

| 组 | readrandom（万次/秒） | readmissing（万次/秒） | seekrandom（万次/秒） | 整次运行的写放大 |
| --- | --- | --- | --- | --- |
| S | 61.4 [49.0-62.8] → 57.5 [52.1-58.7] | 385 → 378 | 14.1 → 14.1 | 5.39 → 5.58 |
| T8 | 49.4 → 46.1 | 285 [252-309] → 227 [177-290] | 7.0 [5.2-9.5] → 5.6 [4.1-7.6] | 2.39 → 2.41 |
| L | 51.5 → 45.9 | 335 → 351 | 9.5 → 10.8 | 4.96 → 4.87 |
| Lseq | — | — | — | 0.95 → 0.95 |

- 读路径没有改动，差别都在同一版本三次之间的浮动里。T8 的读一向取决于停下时剩几个 tier，每次运行都不同（见 [tiered compaction 的记录](2026-10-18-tiered-compaction.md)）。
- manifest 一共只有 5～12 KB，相对一次运行写下的 1.3 GB 可以忽略，写放大不变。

## 结论

- manifest 的代价不在字节，而在 fsync 的次数与位置：每次换状态一次 fsync（约 3 毫秒），放在 `state_lock` 里，会让碰上它的冻结、也就是那一次写入，多等一次 fsync。
- 普通负载下吞吐只差几个百分点，代价主要体现在最大延迟上；冻结极频繁（memtable 小、写入快、不合并）或换状态极频繁（trivial move）时吞吐也会明显下降。
- 改进的方向（还没做，记在交接文档的欠账里）：把 fsync 移出 `state_lock`，像 RocksDB 那样用一个排队的队列保住"记录的先后 = 生效的先后"，并把排队的几条记录攒成一次 fsync；或者让冻结不必等 manifest（冻结不改文件列表）。
- 没有测的：打开一个已有数据库要多久（打开每个 SST 都要读回索引与 Bloom filter）。

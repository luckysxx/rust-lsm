# leveled compaction：穿过空层的复制消失，写放大介于简单分层与 tiered 之间

2026-10-19。要回答的问题：在 L10、L11 的同一组负载下，leveled（按字节的目标、从最底层往上建层、部分合并、trivial move）的写放大、读与空间各是多少；简单分层里"穿过空层的复制"是否消失；顺序写入时 trivial move 能省多少；数据量大十倍时这些差别是否还在。

- 机器：Apple M5（Mac17,2），10 个逻辑 CPU，32 GB 内存，macOS 26.6.2，**使用电池**；内置 SSD，APFS。
- 代码状态：提交 f52656c 之上加了 L12 的工作区，即与本记录一起提交的那一版（`compaction::leveled`、`CompactionOptions::Leveled`、部分合并与 trivial move 的执行；基准驱动新增 `--compaction leveled`、`--level-multiplier`、`--base-level-mb`）。分两批跑：第一批时 trivial move 只挪单个文件；第二批之前改成了几个互不重叠的 L0 文件可以一起挪（见"顺序写入"一节）。随机写入下 L0 的文件彼此重叠，这个改动不起作用：第二批重跑 L 三次，整次运行的写放大 4.52 [4.26-5.10]、扫描 10.2 万次/秒，都在第一批的浮动之内。
- 对照对象：同一天、同一版代码上重跑的简单分层（L0 之下 4 层与 2 层）与 tiered（`num_tiers` 8），不是 L10、L11 记录里的数字。
- 每个配置运行 3 次，下表取中位数，方括号里是三次的最小与最大值。
- 读负载都在后台合并做完之后才开始，读的是合并停下时的形状。

重跑方式（在仓库根目录下，只差后面的合并参数）：

```sh
cargo run --release -p lsm-bench -- --target engine --memtable-mb 4 --block-cache-mb 64 --workloads fillrandom,overwrite,readrandom,readmissing,seekrandom \
  --compaction leveled --l0-trigger 2 --level-multiplier 10 --base-level-mb 8 --max-levels 4    # L：leveled
# L2：同上，--max-levels 2
# S：--compaction simple --l0-trigger 2 --size-ratio 200 --max-levels 4
# S2：同上，--max-levels 2
# T8：--compaction tiered --num-tiers 8
# 顺序写入：把 --workloads 换成 fillseq，分别用 S、T8、L 的参数，另加 L 的 --l0-trigger 1
# 一千万条：在 S、L、T8 的参数前加 --num 10000000
```

基准大小 8 MB 是"memtable 上限 × L0 触发值"（RocksDB 建议的取法，它的默认值 256 MB 就是 64 MB × 4）。数据约 116 MB：写入期间最底层不到 80 MB 时，只有 L3 的目标大于 0（最底层的 1/10），基准层是 L3；最底层超过 80 MB 之后 L3 的目标超过 8 MB，L2 也启用（约 1.2 MB），成为基准层。L1 的目标一直是 0。

## 写：没有了空层的复制，写放大在两者之间

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| S 简单分层，4 层 | 308 [303-315] | 1.10 | 0.95 | 5.73 [5.62-5.87] | 4.83 [4.73-5.02] | 5.32 [5.23-5.35] |
| S2 简单分层，2 层 | 312 [274-315] | 0.75 | 0.73 | 4.18 [4.11-4.32] | 3.82 [3.61-3.98] | 4.00 [3.96-4.05] |
| L leveled，4 层 | 324 [324-327] | 0.82 | 0.90 | 4.51 [3.83-4.54] | 4.42 [4.09-5.26] | 4.32 [4.13-4.89] |
| L2 leveled，2 层 | 323 [304-323] | 0.85 | 0.92 | 4.58 [4.19-4.61] | 4.60 [3.92-4.63] | 4.39 [4.25-4.62] |
| T8 tiered | 325 [315-335] | 0.32 | 0.45 | 2.20 [1.81-2.24] | 2.64 [2.57-2.66] | 2.40 [2.23-2.43] |

- **穿过空层的复制消失了。** 简单分层设 4 层比设 2 层多写约 1.3（5.32 对 4.00），停下的形状却一样（全部在最底层）；leveled 设 4 层与 2 层的写放大在浮动之内（4.32 对 4.39）。L0 直接并进基准层，L1 一直是空的，L2 到最后才启用、只有约 1 MB，没有数据从空层中间穿过。
- **整次运行的写放大介于简单分层（4 层）与 tiered 之间**，与预期一致。
- **但比只设 2 层的简单分层略高**（4.32 对 4.00）。leveled 的基准层一直保持在最底层的约 1/10，每次 L0 并进来都要重写基准层；基准层的文件再一个一个推进下一层，随机 key 下基准层只有 3 个文件，每个与下一层约 1/3 的文件重叠，推下 4 MB 要重写约 40 MB，即每往下推一层约重写 multiplier 倍的数据。简单分层在这组负载下合并跟不上写入，每次拿到一大批 L0 文件一路并到最底层，停下时上面全空，反而少写了。
- **写完之后等后台的时间**比简单分层（4 层）少约四分之一，仍是 tiered 的 2～3 倍。

## 顺序写入：几个 L0 文件一起挪之后，只剩 flush

| 组 | fillseq 吞吐（万次/秒） | 之后等后台 (s) | 写放大 | 停下时 L0 / L1 / … 的 SST |
| --- | ---: | ---: | ---: | --- |
| S 简单分层 | 684 [673-685] | 1.28 | 6.10 [6.03-6.28] | 0 / 0 / 0 / 0 / 26 |
| T8 tiered | 703 [690-704] | 0.35 | 1.90 [1.90-2.12] | 各次不同，3～6 个 tier |
| L leveled，触发值 2，只挪单个文件 | 676 [653-683] | 0.26 | 1.87 [1.87-1.90] | 0～1 / 0 / 0 / 2 / 24～25 |
| L leveled，触发值 1，只挪单个文件 | 688 [662-691] | 0.29 | 1.87 [1.83-1.90] | 0 / 0 / 0 / 2 / 25 |
| L leveled，触发值 2，几个文件一起挪 | 700 [600-727] | 0.23 | 0.95 [0.95-0.95] | 0～1 / 0 / 0 / 2 / 24～25 |
| L leveled，触发值 1，几个文件一起挪 | 708 [704-720] | 0.24 | 0.95 [0.95-0.95] | 0 / 0 / 0 / 2 / 25 |

- **简单分层在顺序写入下写放大高达 6**：顺序写入的文件之间本来不重叠，整层合并与穿过空层的复制全是原样重写。
- **只挪单个文件时，leveled 的写放大约 1.9。** 基准层往下一层是一个文件一个文件地推，顺序写入下与下一层不重叠，全是 trivial move；多出的约 0.9 来自 L0 并进基准层：L0 的任务带上全部 L0 文件，而只有 L0 恰好只有 1 个文件时才能挪。触发值改成 1 也一样：顺序写入每秒约 780 MB，每 5 毫秒左右 flush 出一个文件，compaction 线程每 50 毫秒醒来一次，醒来时 L0 已经积了好几个文件。这些文件彼此不重叠、与基准层也不重叠，合并它们只是原样复制。
- **改成"上层的文件按首 key 排好之后彼此不重叠、下层没有重叠"就一起挪之后，写放大降到 0.95**，即只剩 flush（SST 有前缀压缩，比用户写入的字节略少）。compaction 一个字节都没写。

| L2 leveled，2 层 | 47.8 [46.6-48.7] | 345 [309-347] | 10.6 [9.2-10.6] | 0.98 [0.98-1.03] | 0～1 / 2～3 / 25～26 |
| T8 tiered | 40.3 [40.1-42.0] | 279 [218-282] | 7.1 [5.1-7.3] | 1.34 [1.32-1.66] | 2～3 个 tier |

- **点查与简单分层相同**：每次仍只进入约 1 个 SST。
- **扫描慢一到两成**：leveled 停下时有两三个 sorted run（基准层与下面的层），有时 L0 还剩 1 个文件；简单分层这组负载下全部并到了最底层，只有一个。这是 leveled 稳定时的正常形状，不是退化：简单分层的"全在最底层"来自合并跟不上写入时的整批合并。
- **空间放大 0.98～1.06**，与简单分层接近；tiered 是 1.32～1.66。最底层以上各层合起来只有最底层的约 1/10，旧版本最多多占这么多。
- 读的浮动主要来自停下时 L0 剩不剩 1 个文件（readmissing 时多问一次 Bloom filter）。

| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| S 简单分层，4 层 | 5.88 [5.72-5.89] | 13.3 | 12.1 | 294 [288-315] | 9.1 [8.4-9.4] | 0.98 | 0 / 0 / 0 / 0 / 265 |
| L leveled，4 层 | 4.88 [4.79-5.19] | 9.6 | 9.4 | 272 [254-276] | 7.4 [7.1-7.5] | 1.08 | 0 / 0 / 3 / 26 / 265 |
| T8 tiered | 2.67 [2.66-2.86] | 4.4 | 3.7 | 158 [155-247] | 3.8 [3.6-7.0] | 1.08～1.70 | 2～3 个 tier |

- **三者的排序与差距和一百万条时一样**，写放大各高了约 0.3～0.6（数据多了，要往下推的层也多了）。
- **leveled 用上了三层**：最底层约 1.16 GB，往上依次约 116 MB、11.6 MB，最上面的 L1 只有约 1.2 MB 的目标、是基准层，停下时是空的。形状是标准的 10 倍阶梯（3 / 26 / 265 个文件）。
- **写完之后等后台的时间**：简单分层 12～13 秒，leveled 约 9.5 秒，tiered 约 4 秒。数据大了以后简单分层的整层合并更慢（最底层每次整个重写，1 GB 以上），差距按比例保持。
- 读的规律也相同：leveled 停下时三个 sorted run，扫描比简单分层的一个慢约两成；tiered 剩 2～3 个 tier，扫描只有简单分层的四成。点查都只进入约 1 个 SST（readrandom 三者都约 30 万次/秒，块缓存只有数据的 5%）。

## 结论

- leveled 去掉了简单分层里穿过空层的复制（4 层与 2 层一样），写放大介于简单分层与 tiered 之间，读与空间接近简单分层；数据大十倍时规律不变，并且用到了三层。
- 它的写放大主要来自"每往下推一层约重写 multiplier 倍"，这是 leveled 用来保持每层一个 sorted run 的代价；部分合并在随机写入下省的不是写放大。
- 顺序写入时，只要允许几个互不重叠的 L0 文件一起挪，compaction 就一个字节都不写，写放大从 1.87 降到 0.95；简单分层同样的负载是 6.1。

## 没有测的

- 合并进行中的空间峰值（部分合并应当远小于整层合并）；写入期间的读。
- multiplier、基准大小的其他取值。
- 各层分别写了多少（引擎只有一个 compaction 字节计数），trivial move 的次数。
- 写入受限速、合并完全跟得上时的稳定形状：基准是"全速写完再等后台"，合并每次拿到一大批 L0 文件，这对整层合并的简单分层有利。
- 使用电池；只有单线程写入。

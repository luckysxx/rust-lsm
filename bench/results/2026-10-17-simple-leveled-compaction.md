# 简单分层 compaction：自动合并下的三种放大

2026-10-17。要回答的问题：后台按简单分层策略自动合并之后，读回到了"全量合并一次"的水平没有；为此付出多少写放大；三个参数（L0 触发值、层间比例、层数）各起多大作用；合并跟不跟得上写入。

- 机器：Apple M5（Mac17,2），10 个逻辑 CPU，32 GB 内存，macOS 26.6.2，**使用电池**；内置 SSD，APFS。
- 代码状态：提交 4c04c95 之上加了 L10 的工作区，即与本记录一起提交的那一版（多层状态与读路径、`compaction::simple_leveled`、按任务合并的 `compact_once`、后台 compaction 线程；基准驱动新增 `--max-levels`、`--compaction`、`--l0-trigger`、`--size-ratio`，每段负载之后连同后台合并一起等完）。"修复之后"一节之前的数字都是在归并游标修改之前测的；提交里的归并游标是修改之后的版本，所以按提交重跑时，扫描的数字应当与"修复之后"一节相近。
- 每个配置运行 3 次，下表取中位数，方括号里是三次的最小与最大值。
- 读负载都在后台合并做完之后才开始，所以读的是合并停下时的形状。

重跑方式（在仓库根目录下，五组只差后面的合并参数）：

```sh
cargo run --release -p lsm-bench -- --target engine --memtable-mb 4 --block-cache-mb 64 --workloads fillrandom,overwrite,readrandom,readmissing,seekrandom \
  --compaction none                                                  # A：不自动合并
# B：--compaction simple --l0-trigger 2 --size-ratio 200 --max-levels 4
# C：--compaction simple --l0-trigger 4 --size-ratio 200 --max-levels 4
# D：--compaction simple --l0-trigger 2 --size-ratio 400 --max-levels 4
# E：--compaction simple --l0-trigger 2 --size-ratio 200 --max-levels 2
```

## 读：自动合并之后与全量合并一次的形状相同

吞吐的单位是万次每秒。A 是 L0 积了 55 个文件、从不合并；B～E 合并停下时全部数据都在最底层（见下一节），四组读的数字在浮动之内，只列 B。

| 负载 | A 不合并 | B 自动合并 | 倍数 | 每次点查进入的 SST（A → B） | 每次点查从文件读的块（A → B） |
| --- | ---: | ---: | ---: | --- | --- |
| readrandom | 29.8 | 51.6 | 1.7 | 1.21 → 0.99 | 0.75 → 0.41 |
| readmissing | 40.4 | 359 | 8.9 | 0.55 → 0.01 | 0.36 → 0.00 |
| seekrandom | 0.70 | 9.29 | 13 | — | — |

- 点查的数字与 [全量 compaction](2026-10-15-full-compaction.md) 记录里合并之后的一致（readrandom 54.3 万、readmissing 376 万，差在浮动之内）：同样是一层范围互不重叠的文件，每次点查最多进入一个文件。
- 不用任何人调用，空间放大也从 1.95 降到 0.98：覆盖写留下的旧版本在合并时丢掉了。
- **扫描比 L09 记录的慢了约三成**，原因与修复见后面两节。

## 写：写放大 4～6，其中两成到三成是"穿过空层"的复制

| 组 | 参数 | fillrandom 吞吐（万次/秒） | 之后等后台 (s) | fillrandom 写放大 | overwrite 写放大 | 整次运行的写放大 | 停下时 L0 / L1 / … |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| A | 不合并 | 332 [315-334] | 0.14 | 0.96 | 0.98 | 0.97 | 55 / 0 / 0 / 0 / 0 |
| B | 触发 2，比例 200%，4 层 | 302 [295-327] | 1.15 [1.13-1.24] | 6.12 [5.94-6.40] | 4.90 [4.87-5.05] | 5.49 [5.49-5.65] | 0 / 0 / 0 / 0 / 27 |
| C | 触发 4，比例 200%，4 层 | 321 [305-337] | 0.94 [0.93-1.23] | 5.02 [5.02-6.12] | 4.98 [4.91-5.03] | 5.03 [5.00-5.51] | 0 / 0 / 0 / 0 / 27 |
| D | 触发 2，比例 400%，4 层 | 295 [294-303] | 1.14 [1.11-1.16] | 5.98 | 5.00 | 5.49 | 0 / 0 / 0 / 0 / 27 |
| E | 触发 2，比例 200%，2 层 | 308 [294-320] | 0.71 [0.68-0.91] | 4.07 [3.97-4.67] | 3.75 [3.75-3.78] | 3.86 [3.86-4.21] | 0 / 0 / 27 |

整次运行的写放大 = flush 与 compaction 写出的字节 ÷ 用户写入的字节，两段写负载一共 232 MB。

- **代价是写放大从 1 涨到 5 左右。** 只合并一次时（L09）是 1.46；自动合并让每条数据被重写好几次。
- **E 只有 2 层，写放大比 B 少了约 2，停下时的形状却完全一样**（全部在最底层）。多出来的 2 就是数据穿过空的 L2、L3 时的原样复制：下层是空的，合并只是把上层重写一遍，什么也没去掉。这正是 trivial move 与"从最底层往上建层"（RocksDB 的 `level_compaction_dynamic_level_bytes`）要省掉的部分，留到 L12。
- **比例 400%（D）与 200%（B）没有区别。** 停下时只有最底层有文件，相邻两层的比例检查几乎不起作用：每一批数据都穿过空层，直接并进最底层。
- **触发值 4（C）的结果分成两种**：两次 5.02、一次 6.12。数据进 L0 的速度远快于合并，L0 一次积多少文件取决于当时的时机，见下一节。

## 合并跟不上写入

- fillrandom 0.33 秒写完 116 MB，之后还要等 1.15 秒，后台合并才做完（A 只等 0.14 秒，那是最后几张表的 flush）。按 B 的数字，合并每秒大约写出 400 MB，而要跟上每秒 320 MB 的写入、写放大又是 5 的话，需要每秒 1.6 GB。
- 所以写入期间 L0 的文件越积越多，合并每次拿到的是一大批 L0 文件，下层相对这一批总是"不够大"，结果一路并到最底层。停下时全部数据都在最底层，就是这个原因：这不是策略在稳定写入下的形状，而是"写入一阵猛灌、之后让合并慢慢追"的形状。
- 这次测到的写放大因此偏低：L0 积压得越多，每次合并摊到的数据越多。写得慢一些、合并来得及时，同样的策略会合并更多次。
- 写入期间 L0 一直在积压，这时候的读会很慢，但这组负载只在合并做完之后才读，没有测到。这正是欠账里的写入停顿（write stall）要解决的问题：L0 太多时让写入慢下来，等合并追上。
- 写入的吞吐只比 A 低约一成：后台合并与写入抢 CPU，但没有任何机制让写入等它。

## 扫描慢了约三成：多出来的一层归并

同样是全量合并之后、全部数据在一层里，在 L09 的提交上 seekrandom 是每秒 13.3 万次，这一版是 9.4 万次；层数设成 1 也一样，所以与层数无关。

原因是读路径推广到多层时，扫描在各层的串接游标外面多套了一层归并游标（`MergeIterator<SstConcatIterator>`），每次前进都要经过它。而 `MergeIterator::next` 每次都把当前 key 复制进一个新分配的 `Vec`，再把堆顶的来源取出、前进、放回。只有一个来源时这些都是白做的。

在一个副本里给 `next` 加一条捷径（堆里只剩一个来源时原地前进，不复制 key、不出堆入堆），同样的负载回到每秒 13.2～14.1 万次、p50 6.9 微秒，确认三成的差距全部来自这一层。

## 修复之后：把当前来源拿在堆外

归并游标改成 mini-lsm 的结构：当前胜出的来源单独放在堆外，前进时它的 key 留在原处可以直接比较，不再复制；单个来源时堆是空的。与上面同样的方式各跑 3 次（中位数，方括号里是最小与最大值）：

| 组 | 负载 | 修复之前 | 修复之后 |
| --- | --- | ---: | ---: |
| B（全部数据在最底层，扫描时只有一个来源） | seekrandom（万次/秒） | 9.29 [9.01-9.29] | 12.1 [12.0-12.6] |
| B | seekrandom 的 p50（微秒） | 10.09 | 7.42 |
| A（55 个 L0 文件，扫描时 55 个来源） | seekrandom（万次/秒） | 0.70 [0.69-0.70] | 0.70 [0.70-0.71] |

- 单个来源的扫描快了三成，接近 L09 的 13.3 万次。这一轮的点查（不经过归并游标）也比上面几轮慢约 5%（readrandom 48.8 万次对 51.6 万次），说明这一轮整体偏慢；按这个比例折算，扫描与 L09 的差距在浮动之内。
- 55 个来源时没有变化：一次扫描的 142 微秒几乎都花在给 55 个文件各建一个游标、各读一个块上，`next` 本身不是瓶颈。
- 写入、写放大、各层形状与修复之前相同（B 组 fillrandom 写放大 6.15，停下时 `0 / 0 / 0 / 0 / 26`）。

## 没有测的

- 合并与写入同时进行时前台的延迟，以及写入期间的读（见上）。
- 写入受限速时（合并跟得上时）的形状与写放大。
- 比较字节数而不是文件数的策略（L12）。
- 使用电池；只有单线程写入。

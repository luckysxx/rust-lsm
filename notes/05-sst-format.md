## 文件的组成

```
┌──────┬──────┬───┬────────┬──────────────────┬────────────┬──────┐
│ 块 0 │ 块 1 │ … │ 块 n-1 │ 索引              │ 索引的起点  │ 魔数 │
└──────┴──────┴───┴────────┴──────────────────┴────────────┴──────┘
  数据块，一个接一个             每个块一项          4 字节       4 字节

索引：      块数（4 字节）│ 第 0 项 │ 第 1 项 │ …
索引的一项： 块的起点（4 字节）│ 首 key 长度（2 字节）│ 首 key │ 末 key 长度（2 字节）│ 末 key
```

所有整数都是大端。与块的尾巴是同一个办法：内容在前，索引在后，最后几个字节指回索引；写的时候数据块一个个追加，封口之前不知道有多少块。

**索引里记什么。**

- 块的起点与首 key 必须有：前者用来读块，后者用来判断一个 key 可能在哪个块。
- 块的长度不记。它等于下一个块的起点减自己的起点；最后一个块用索引的起点来减。
- 块的末 key 记。定位只需要首 key，这与 B+Tree 的内部节点只存每个孩子的最小 key 相同。但 LSM 还需要整个文件的 key 范围：L0 的文件之间范围可以重叠，查询要靠"文件的首 key 到末 key"判断有没有交集，没有就整个跳过；compaction 选文件时也看范围是否重叠。文件的首 key 是第一个块的首 key，文件的末 key 只能来自最后一个块的末 key；从后一个块的首 key 只能知道"比它小"，得不到末 key 本身。

**魔数。** 文件最后 4 字节固定为 ASCII 的 `LSM1`，打开时先核对，不是就说明这不是引擎写的文件或者文件被截断了。作用与 B+Tree 的 meta 页里的魔数相同，见 [文件格式与元数据校验](../../storage/notes/05-storage-recovery/03-file-format-and-meta-validation.md)。

**例子**：两条记录 `a → 1`、`b → 2`，块的目标大小小到每块只放一条，共 52 字节。

```
       00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x00 │ 00 01 61 00 01 31 00 00 00 01 00 01 62 00 01 32 │ ..a..1......b..2
0x10 │ 00 00 00 01 00 00 00 02 00 00 00 00 00 01 61 00 │ ..............a.
0x20 │ 01 61 00 00 00 0A 00 01 62 00 01 62 00 00 00 14 │ .a......b..b....
0x30 │ 4C 53 4D 31                                     │ LSM1
```

- `[0, 10)`、`[10, 20)`：两个数据块，各是一条记录、偏移数组 `00 00`、条数 `00 01`。
- `[20, 24)`：块数 2。
- `[24, 34)`：第 0 项，起点 0，首 key `a`，末 key `a`。
- `[34, 44)`：第 1 项，起点 10，首 key `b`，末 key `b`。
- `[44, 48)`：索引的起点 20（`0x14`）。
- `[48, 52)`：魔数。

## 构建

SST 的构建器手里有一个正在装的块、已经封口的块攒成的字节、一张索引：

```
加入一条记录：
    交给正在装的块
    它放不下 → 封口：编码，在索引里记一项（起点、首 key、末 key），接到字节后面
               换一个新的空块，再加一次
    记下正在装的块的首 key（只在第一条时）与末 key（每次更新）

写成文件：
    封最后一个块
    接上索引，再接上索引的起点与魔数
    写入文件，同步
```

这就是 [块满与过大的记录](04-block-format.md#块满与过大的记录) 里说的"由上层开新块"的那个上层。顺序上有两处与块的构建器相同的讲究：先记起点再接数据（起点是接上去之前的长度）；索引的起点要在接索引之前取。

全部内容先攒在内存里，最后一次写出。flush 一张 memtable 时文件的大小与 memtable 相当，多占一份内存可以接受。

## 落盘需要哪几步

要保证断电之后一个新建的文件还在，需要：

```
写入内容 → fsync 文件 → fsync 父目录
```

`fsync` 文件保证内容与长度落盘；`fsync` 父目录保证"目录里有这个文件名"落盘。LSM 不断新建文件，后一步比单文件的 B+Tree 常用得多。

不需要 `rename`。`rename` 用来原子地替换一个已有的文件；新的 SST 用的是没有用过的文件名，没有东西要替换，创建时遇到同名文件直接报错。

写到一半崩溃留下的残缺文件不要紧：文件在登记进 MANIFEST 之前没有人引用，重启时作为残留删除，见 [manifest](13-manifest.md)。

## 读块的方式：`pread` 与 mmap

| | `pread` | mmap |
| --- | --- | --- |
| 用法 | 把文件里从某个位置起的若干字节拷到自己的缓冲区 | 把文件映射成一段内存，像读数组一样读 |
| 每次读 | 一次系统调用，一次拷贝 | 没有系统调用与拷贝；第一次碰到某页时内核去读盘 |
| 读到的字节归谁 | 归调用方 | 归映射，拿到的是指向映射内部的切片 |
| 读盘出错 | 返回一个错误 | 进程收到信号 |
| 缓存 | 自己做，自己决定留多少、淘汰谁 | 内核的页缓存，无法控制 |

SST 写完不改，没有用 mmap 写入时"落盘顺序不受控"的问题，用 mmap 读是可行的，LevelDB 对一部分文件就这样做。本项目用 `pread` 加自己的块缓存，RocksDB 的默认做法与 mini-lsm 也是如此。理由：块之后要校验、要解压，读进来必须先处理，mmap 省不掉那次拷贝；读盘出错是可以处理的返回值；缓存的容量与淘汰由引擎决定；读出的字节由块自己拥有，块不必借用映射。

mmap 的机制与代价见 [页缓存与 buffer pool](../../storage/notes/02-cache-pager/07-page-cache-versus-buffer-pool.md)。

## 错误类型

从这一篇开始引擎要读写文件，函数会失败。引擎是库，调用方要按失败的种类做不同的事，所以用自己的枚举（[error.rs](../engine/src/error.rs)）：

- `Error::Io`：读写文件失败，里面是操作系统报告的原因。
- `Error::Corruption`：文件内容不符合格式，里面是一句说明。

可能失败的函数返回 `Result<T>`。调用方违反约定（空的 key、给无效的游标取值）仍然用断言，不属于这两种。枚举、`From` 与 `?` 的机制见 [[rust-learning/notes/07-errors/02-定义自己的错误类型|定义自己的错误类型]]，手写枚举、`thiserror` 与 `anyhow` 的选择见 [[rust-learning/notes/07-errors/05-库错误与应用错误的接口选择|库错误与应用错误的接口选择]]。

## 打开与读取

```
打开：    读末尾 8 字节 → 核对魔数 → 得到索引的起点 → 读出索引，留在内存里
读一个块：从索引得到它的范围 → 读出这段字节 → 解码
定位：    在索引上找到块 → 读这个块 → 块内定位
前进：    块内前进；走到块尾就读下一个块
```

打开时只读文件末尾和索引，数据块一个都不碰。之后每读一个块是一次 `pread`。

**块的范围。** 起点在索引里；终点是下一个块的起点，最后一个块的终点是索引的起点。`pread` 要的是起点与长度，长度是终点减起点。

**找块用末 key。** 要找的是"第一条 key 大于等于给定 key 的记录"所在的块，也就是第一个末 key 大于等于给定 key 的块。与 [块内定位](04-block-format.md#块内定位) 是同一个二分，只是比较的对象从记录的 key 换成了块的末 key。

```
块：        [a … c]   [d … f]   [g]
给定 key：   b → 块 0     cc → 块 1     z → 没有这样的块
```

给定的 key 落在两个块之间时（上面的 `cc`），直接得到后一个块，它的第一条就是答案。如果只用首 key 找"最后一个首 key 不大于它的块"，会先落到前一个块，在块内走到头之后再换下一个块；mini-lsm 的教程用的是这种，并指出也可以用末 key。给定的 key 比文件里所有 key 都大时没有这样的块，游标无效。

**SST 的游标**（`SsTableIterator`）记着"现在在第几个块"，手里拿着这个块上的一个游标；任何时刻只拿着一个块。它有效与否完全由块上的游标决定。前进时先让块上的游标前进，它走到块尾而后面还有块，就读下一个块、换上新块的游标。游标拿着 SST 的一个 `Arc`，所以 SST（打开的文件与索引）在游标用完之前不会被释放。

读下一个块可能失败，所以游标的"前进"返回一个结果，见 [前进可能失败](03-iterators-and-merge.md#前进可能失败)。

## 不信任文件的内容

内存里的数据由程序自己构造，可以相信；从文件读回来的字节不能。文件可能被截断、被别的程序改过，或者根本不是引擎写的。读到不合格的内容要返回一个"内容损坏"的错误，不能越界或 panic，也不能把错的内容当成对的继续用。

检查分三处，各管自己读到的东西：

| 位置 | 检查 |
| --- | --- |
| 打开文件 | 文件够不够放下末尾的 8 个字节；魔数对不对；索引的起点是否在文件里 |
| 解码索引 | 每一项读得全不全；后面有没有多余的字节；至少有一个块；第一个块从 0 开始；起点严格递增并且在索引之前；每个块的首 key 不大于末 key，并且大于前一个块的末 key |
| 解码数据块 | 读得出条数且不为 0；偏移数组没有超出块；每条记录的起点从 0 开始、严格递增、落在数据区里；两个长度恰好把记录占满 |

顺序上要先检查、再使用：例如先确认文件不短于 8 个字节，再去算"末尾 8 个字节从哪里开始"，否则无符号数相减会下溢。

这些都是结构上的检查。字节被改动之后恰好仍然符合格式的情况（比如 value 里的一个字符变了）发现不了，要靠校验和，见 [写批次与校验和](15-write-batch-and-checksums.md)。

错误与断言的分界：文件的内容不对，是运行时可能发生的事，返回错误；调用方传了越界的块下标，是程序写错了，用断言。

## 块缓存

**要省掉什么。** 没有缓存时，每次读块都要做一遍：系统调用 `pread`、分配一块内存、把字节复制进来、解码偏移数组；以后还有校验和，可能还有解压。即使字节已经在操作系统的页缓存里、不用真正读盘，这些也省不掉。热门的块会被一遍遍重读。块缓存把解码好的块留在内存里，再次用到时直接拿走。

**与旁路缓存是同一个模式。** 业务里常见的做法是在数据库前面放 Redis：先查缓存，没有就查数据库，再把结果放进缓存。块缓存是一样的结构，只是缓存在进程内，被缓存的东西是块：

| | Redis 放在数据库前面 | 块缓存放在 SST 文件前面 |
| --- | --- | --- |
| 键 | 业务自己定，如 `user:42` | `(SST 编号, 块下标)` |
| 值 | 序列化后的结果 | 解码好的块，`Arc<Block>` |
| 没命中 | 查数据库，写回缓存 | 读文件、解码，放进缓存 |
| 满了 | `maxmemory` 加淘汰策略 | 容量上限加淘汰策略 |
| 数据被改了 | 要删缓存或更新缓存，处理不好就不一致 | 不会发生：SST 写完不再修改 |

最后一行是两者最大的差别。旁路缓存最难的部分是缓存与数据库的一致，见 [[_knowledge/后端/03-缓存问题与并发更新|缓存问题与并发更新]]。块缓存没有这个问题，原因有两条：SST 不可变，一个块的内容从写出那一刻起就不再变化；SST 的编号只增不减、不会重用，一个键永远只对应一个块。compaction 删掉一个文件时，它留在缓存里的块也不用主动清理：不会再有人用这个编号来查，它们会被慢慢淘汰掉。

键里必须有 SST 编号：每个文件都有第 0 块，只用块下标会把不同文件的块混在一起。

**为什么缓存块，而不是一条条记录。**

- **块是读和解码的最小单位。** 要拿到一条记录，本来就得把整个块读进来、解码；把块留下不增加任何工作，同一块里的邻居也一起留下了。
- **范围扫描用得上。** 扫描要的是"某个 key 之后的下一条"。缓存了一些单独的记录，并不能说明它们之间没有别的记录，扫描用不上；缓存了块，块内的记录是完整、连续的。
- **"不存在"也能回答。** 点查要找的 key 落在某个块的范围里、块里却没有，就说明这个文件里没有它。按记录缓存的话，"没有"本身也得缓存起来，否则每次都要回到文件。
- **每一项的额外开销是固定的。** 缓存里的每一项都要付哈希表条目、计数、淘汰用的记录，几十个字节。记录只有几十字节时，开销比数据还大；一个几 KB 的块分摊下来可以忽略。
- **不需要失效。** 块属于一个不可变的文件。按 key 缓存"最终结果"的话，每次写入都会让它过时，又回到了旁路缓存的一致性问题。

代价是只有一条记录热门时，也要把它所在的整个块留在内存里。点查极多、热点很分散而数据量很大时，这会浪费内存，所以有的引擎另外提供按记录的缓存：RocksDB 的 row cache 用"文件编号加 key"作为键，缓存的是某个文件里的某条记录，仍然属于不可变的文件，不需要失效；Cassandra 有 key cache，记下某个 key 在某个文件里的位置。它们都是块缓存之外的补充，不是替代。

**三个组成部分。** 查找：一张哈希表，从键找到块。装入：没有命中时读盘、解码，放进表里。淘汰：表满了，要先丢掉一个，才能放进新的。前两部分就是一个 `HashMap`；要动脑筋的是第三部分，也就是淘汰策略。

**LRU（最近最少使用）。** 满了就丢掉最久没有被访问的那一个。实现上，一张哈希表加一条双向链表：链表按最近访问的时间排列，每次命中都把这一项挪到表头，淘汰时从表尾拿走。容量为 3 时：

```text
访问 A B C      链表 C B A        （表头最近访问过）
访问 A          链表 A C B        命中，A 挪到表头
访问 D          链表 D A C        满了，淘汰表尾的 B
```

LRU 有两个问题：

- **读也要改链表。** 命中之后要把这一项挪到表头，所以每一次读都要修改共享的链表，多个线程同时读也得排队拿锁。RocksDB 的 `LRUCache` 把缓存按键的哈希分成多份，每份一把锁；它的 `HyperClockCache` 改用 CLOCK 类的做法，命中时只设置一个标志位，不移动位置。
- **一次大范围扫描会冲掉热门的块。** 扫描会把一长串只用一次的块依次放进表头，原来反复用到的块被挤到表尾淘汰掉。扫描结束后，缓存里留下的全是不会再用的块。这叫缓存污染。

**TinyLFU。** Rust 的缓存库 `moka` 用的是这一类策略：除了"最近有没有用过"，还用一个很省内存的计数结构，近似地记下每个键最近被访问的次数。新块要进来、需要腾位置时，比较新块和将要被淘汰的那一块谁的访问次数多：新块不如它，就不放进来。扫描带来的块都只访问一次，挤不掉被反复访问的块。

**两层缓存。** 用 `pread` 读文件时，操作系统的页缓存仍然在工作：同一个块可能在页缓存里存了一份原始字节，又在块缓存里存了一份解码后的结果。RocksDB 提供 direct I/O 来绕过页缓存，把内存都留给自己的缓存；本项目不做。

**容量按块在内存里的大小算。** 容量是给缓存的内存预算，所以计入的是块解码之后实际占用的内存，不是它在文件里的长度。本项目的块不压缩，两者只差几个字节；启用压缩之后，一个在文件里 4 KB 的块解压后可能是 16 KB，按文件里的长度计，缓存实际用掉的内存会远超预算。

**本项目的实现。** 缓存用 `moka`（`BlockCache` 与 `new_block_cache`，在 `table.rs`），每个块按 `Block::memory_size` 计重，容量由选项 `block_cache_size` 给出（字节）。引擎打开时建一个缓存，flush 写出的每个 SST 都拿着它的 `Arc`；`read_block` 先查缓存，没命中再调用 `read_block_from_file`，读成功才放进缓存。没有用 moka 的 `try_get_with`（多个线程没命中同一个键时只加载一次）：它把错误包成 `Arc<Error>` 交给所有等待的线程，而引擎的错误里装着 `io::Error`，无法从 `Arc` 里还原；分开写 `get` 与 `insert` 的代价是同时没命中时会多读一次文件，块不可变，结果仍然正确。

**工业实现。** mini-lsm 用 `moka::sync::Cache<(usize, usize), Arc<Block>>`，容量按条数。GreptimeDB mito2 的 `CacheManager`（`src/mito2/src/cache.rs`）里有十几种缓存，都用 moka，容量按字节算；它的 SST 是放在对象存储上的 Parquet 文件，所以除了内存里的缓存，还有一层本地磁盘上的文件缓存。

## 块的压缩

本项目的块不压缩，mini-lsm 也不做。压缩本身的原理见 [[_knowledge/数据库/08-数据压缩|数据压缩]]；这里只记它在 SST 格式里的位置。

- **在写 SST 的时候压缩。** 压缩放在构建器封口一个块的地方：块编码完，整块交给压缩算法，写进文件的是压缩后的字节，索引里记的是压缩后的起点。flush 和 compaction 都通过构建器写文件，两条路都会压缩；compaction 读旧文件时解压，写新文件时再压缩，可以趁机换一种算法。读的时候读出压缩后的字节、解压、再解码。按块压缩，读一条记录只需要解压一个块。
- **memtable 一般不压缩。** 它还在接收写入，查找要随机访问其中任意一条，压缩之后每次插入和查找都要先解压。它本身只是一段时间的写入，内存不是瓶颈时没有必要。例外是内存紧张、又能整批处理的场合：GreptimeDB mito2 的 `BulkMemtable` 会把攒得足够大的一批行在内存里编码成带 zstd 压缩的 Parquet（`EncodedBulkPart`，见 `src/mito2/src/memtable/bulk/part.rs` 的 `BulkPartEncoder`），用 CPU 换取同样的内存能放更多数据；源码里也留着一句"是否需要压缩"的 TODO。
- **每个块带一个标记。** 说明这个块用的是哪种算法；压缩之后没有变小的块存原样，标记为不压缩。LevelDB、RocksDB 把这个标记和校验和一起放在每个块的末尾。
- **缓存里放解压之后的块。** 解压是读路径上最花 CPU 的一步，缓存命中就省掉它；缓存的容量也按解压之后的大小算。
- **不同的层用不同的算法。** RocksDB 允许按层设置：上面几层的数据很快会被 compaction 重写，用快的 LZ4 或不压缩；最底层的数据最多、放得最久，用压缩率高的 zstd。
- **按列存储的引擎先编码、再压缩。** GreptimeDB mito2 的 SST 是 Parquet 文件，整体用 zstd 压缩；时间戳列和序号列另外指定差值编码（`DELTA_BINARY_PACKED`），见 `src/mito2/src/sst/parquet/writer.rs`。按行存储的 LSM 能做的类似的事是 key 的前缀压缩，见 [L08](08-bloom-filter-and-prefix-compression.md)。

## 常见错误

- **换块之前就记下首 key，或者只在换块时记首 key。** 前者把上一个块的最后一条记成了新块的首 key；后者漏掉整个文件的第一个块，它不是换块换出来的。
- **先接数据、后记块的起点。** 起点记成了块的终点。索引的起点同理，要在接上索引之前取。
- **放不下的那条记录没有重新加入新块。** 每换一次块丢一条记录。
- **最后一个没装满的块没有封口。** 文件里少了末尾的若干条记录。
- **把块的终点当作长度传给读文件的函数。** 从 0 开始的第一个块碰巧读对，其余的块读多了或者读到文件外面。
- **最后一个块的终点取成文件的末尾。** 把索引和尾部的 8 个字节也当成了块的内容。
- **魔数与索引的起点读反了位置。**
- **走到块尾的判断写反。** 块上的游标还有效时就换块，结果只给出每个块的第一条。
- **换块时忘了更新"现在在第几个块"。** 之后一直在重读同一个块。
- **错误信息只写"内容损坏"。** 种类本身已经表达了这层意思；信息里要写的是哪一项检查没有通过。

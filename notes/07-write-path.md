# 写路径

## 位置

[全景](README.md#全景)的第 ④ 步：把冻结的 memtable 写成 L0 的一个 SST。[SST 格式](05-sst-format.md) 提供了写文件的工具，[读路径](06-read-path.md) 已经让读取看得见 L0，这一篇把两者接上。做完之后内存不再无限增长，数据真正落到磁盘上。

## flush 做什么

```
取最旧的一张冻结的 memtable（列表的末尾）
把它的全部记录按顺序写成一个 SST 文件，同步文件，同步目录
换状态：冻结列表去掉这张表，L0 的最前面加上这个 SST
```

**先 flush 最旧的。** 冻结列表里新的在前，L0 里也是新的在前。按从旧到新的顺序 flush，每次把结果放到 L0 的最前面，两个列表里的新旧关系就一直是对的。

**墓碑照常写进文件。** 更旧的 SST 里可能还有这个 key 的值，要靠墓碑盖住。在 flush 时丢掉墓碑，被删除的值会在下次读取时复活。墓碑什么时候可以真正丢弃，见 [compaction 的执行](09-compaction-execution.md)。

**空的表不写文件。** 一条记录都没有的 SST 没有意义，直接把这张表从列表里拿掉。

**文件的编号**从一个只增不减的计数器取，不重复使用；文件名由编号得到。

## 顺序与加锁

写文件慢，换状态快，两者分开：

```
拿 flush 的锁（同一时刻只做一次 flush）
    看最旧的冻结表是哪张
    写文件、同步              ← 慢；这期间读、写、冻结都照常进行
    拿改结构的锁，再拿状态的写锁
        复制状态，去掉那张表，加上 SST，换指针   ← 一瞬间
```

- **写文件期间不占着状态的锁。** 被 flush 的表已经冻结，不会再变，读它不需要任何锁；读者手里的快照也不受影响。
- **换状态是一步。** 读者取到的快照要么是"表还在、文件不在"，要么是"表不在了、文件在"，没有两边都缺或者两边都有的时刻。
- **先落盘，后换状态。** 状态里出现的 SST 都是已经写完并同步的。这与 B+Tree 的 [提交顺序](../../storage/notes/05-storage-recovery/04-commit-order-and-sync.md)"数据页 → 同步 → meta"是同一个次序，状态指针在这里扮演 meta 的角色；等有了 [manifest](13-manifest.md)，登记进 manifest 的那一步接在落盘之后、换状态之前。
- **失败时状态不变。** 写文件出错就带着错误返回，那张表仍在冻结列表里，数据照样读得到，之后可以重试。写到一半的文件留在目录里，没有任何地方引用它。
- **flush 之间要排队。** "看最旧的是哪张"与"把它拿掉"之间不能插进另一次 flush，否则两次 flush 会写同一张表。冻结不必与 flush 排队：冻结只往列表的开头加，不碰末尾。

旧的表被拿出状态之后并不立刻释放：flush 之前建立的扫描游标还拿着它，等这些游标用完它才释放。见 [谁拿着什么](README.md#谁拿着什么)。

## 谁来触发：后台线程

flush 要读完一整张表、写文件、同步，耗时以毫秒到秒计。放在写入的调用里做，那一次写入就要等这么久；所以引擎专门留一个线程做这件事，写入只负责冻结和通知。

```
写入的线程                         后台的 flush 线程
─────────────────                  ──────────────────────────
写进可写的表                        睡在通道上（最多睡一个间隔）
表满了 → 冻结
        → 发一个"有活了" ────────→ 醒来
继续写下一条                        把冻结的表一张一张写成 SST，直到一张不剩
                                   回去睡
```

**两层结构。** 线程活得比启动它的函数久，要用的东西只能整个交给它。于是引擎分成两层：里面一层（`LsmStorage`）只管数据怎么组织，不起线程；外面一层（`Db`）用 `Arc` 包着里面那层，自己留一份指针，另一份交给线程，同时保存线程的把手和通道的发送端。对外的接口都在外面这层。

**怎样等：通知加超时。** 线程睡在通道的"带超时的接收"上。通知让 flush 在冻结之后立刻开始；超时是兜底，哪一次通知没有发出、或者上一轮 flush 失败了，到点它也会自己醒来再看一次。两种方式各有只用一种的做法：只靠定时醒来（mini-lsm 每 50 毫秒看一次）最简单，代价是冻结之后最多白等一个间隔；只靠通知最及时，但失败之后的重试要另外安排。

**醒来做多少：做到一张不剩。** 写入快的时候，一次 flush 期间可能又冻结了几张。每次醒来只写一张的话，积压靠后续的通知和超时慢慢消化；一直做到没有冻结的表，积压最快消掉。

**失败了怎么办。** 后台线程里出的错没有调用方可以交。这里的做法是把错误打印出来，线程继续运行，下一轮再试；没写成的表还在冻结列表里，数据没有丢，读取照常。磁盘一直写不进去时冻结的表会越积越多，这要靠[写入停顿](#大纲)和"后台持续失败时拒绝写入"来兜住，目前都还没有。

**通知是轻的。** 写入的线程只往通道里放一个很小的值，不等对方处理。通知发多了没有害处：线程醒来发现没有活就回去睡。

## 关闭

```
通知后台线程结束，等它真的结束      ← 它手上正在写的那张表会先写完
冻结可写的表                        ← 这张表里也有数据
把冻结的表全部写成 SST
```

- **先停线程，再收尾。** 停的只是后台那个调用者，flush 这个动作谁都可以做：线程停了之后，冻结和 flush 由调用关闭的这个线程自己完成，后台没来得及写的表也在其中。这样关闭无论成功还是失败，返回时后台都已经没有任何动作，调用方可以放心地删目录、退出进程。
- **停线程放在最后也能得到同样的结果**：flush 之间本来就要排队，关闭的线程与后台线程同时做不会写同一张表。差别在写文件失败的时候：关闭提前带着错误返回，后台线程却还在运行，"关闭失败之后是什么状态"就不好说清楚了。
- **冻结必须在 flush 之前**，否则可写的表里的数据不会落盘。
- **可写的表也要落盘。** 在有 [WAL](14-wal.md) 之前，memtable 里的数据只在内存里，关闭时不写就丢了。有了 WAL 之后这一步可以省，重启时从日志恢复；多数引擎仍然在正常关闭时做，换取下次启动不用重放。
- **关闭是显式调用的，并且返回错误。** 写文件可能失败，调用方需要知道。值被释放时自动执行的清理只负责让线程停下，不做 flush：它没有办法把错误交出去。
- **没有调用关闭就退出**，相当于一次崩溃：最后那部分还在内存里的数据没有了，已经写成的 SST 不受影响。

## 写入为什么暂时不返回错误

目前 `put` 与 `delete` 不返回 `Result`，`get` 与 `scan` 返回。区分的依据是：这次调用会不会碰到它控制不了的东西。

- **写入只动内存。** 插进跳表，必要时冻结（换一个指针）。写文件发生在后台线程里，不在写入这条路径上，它的错误由后台线程自己处理。内存分配失败在 Rust 里是直接终止进程，不是一个可以返回的错误。
- **读取可能读文件。** 要查的 key 不在内存里时会读 SST 的块，读盘可能失败（`Io`），读出来的内容可能不对（`Corruption`）。

空 key、空 value 用 `assert!` 拦下：这是调用方违反了约定，调用方自己就能避免，属于程序的错误而不是运行环境的失败。原则是：调用方无法预防的失败返回 `Result`，调用方违反约定用 panic。

这个签名是暂时的。下面几件事都会让写入变得可能失败，届时 `put` 改为返回 `Result`：

- **WAL**（[L14](14-wal.md)）：写入要先追加日志并同步，写盘可能失败。
- **后台持续失败时拒绝写入**：RocksDB 把后台的写盘失败记为 background error，此后的写入直接返回这个错误。
- **长度上限**：key 与 value 来自程序外部（命令行、网络）时，超长是输入的问题而不是调用方的程序错误，应当返回错误而不是 panic。

LevelDB、RocksDB 的 `Put` 从一开始就返回 `Status`，mini-lsm 的 `put` 也从一开始就返回 `Result<()>`：它们预先为 WAL 留好了位置，接口以后不用再改。本项目先按当前的实际情况写，到 WAL 时再改，这次改动由编译器找出所有调用处。[L14](14-wal.md) 已改为返回 `Result`：追加 WAL 可能失败，超长的 key 或 value 返回 `InvalidArgument`；空 key、空 value 仍是 panic。

## 常见错误

- **flush 时过滤掉墓碑。** 更旧的文件里的值复活。
- **拿掉的是最新的那张表，或者新文件放到了 L0 的末尾。** 新旧顺序颠倒，旧值盖住新值。
- **写了文件却没有把表从冻结列表里拿掉。** 同一张表被反复 flush，文件越来越多。
- **拿掉了表却没有把文件放进 L0。** 这张表里的数据从读取中消失。
- **喂数据的循环里忘了让游标前进。** 同一条记录被无休止地加进文件。
- **整个 flush 期间一直持有改结构的锁。** 冻结排在它后面，写入在写文件的这段时间里全部停住。
- **后台线程遇到一次写失败就结束了。** 之后再也没有人做 flush，冻结的表只增不减，而写入的一方毫无察觉。
- **后台线程不处理"发送端已经不在"。** 它永远不会结束，而且每一轮都立刻返回，空转占满一个核。
- **关闭时只 flush 了冻结的表，没有先冻结可写的那张。** 最后写入的数据没有落盘。
- **关闭时没有等后台线程结束。** 进程退出时它可能正写到一半。

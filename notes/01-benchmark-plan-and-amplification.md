# 基准方案与三种放大的测量

状态：部分已整理 · 代码：[stats.rs](../engine/src/stats.rs) 的 `Stats`、`StatsSnapshot`；[workload.rs](../bench/src/workload.rs)、[runner.rs](../bench/src/runner.rs)、[target.rs](../bench/src/target.rs)；结果在 [bench/results](../bench/results/README.md)

## 问题

LSM 里很多机制不改变读出来的结果，只改变代价：去掉 Bloom filter，所有测试照样通过，只是查不存在的 key 变慢；三种 compaction 策略读到的数据完全相同，差别只在磁盘被写了多少遍、占了多少空间。这类机制有没有用、值不值它的代价，测试回答不了，只能靠数字。

LSM 的代价通常用三种放大描述（定义见存储笔记[B+Tree 与 LSM](https://github.com/luckysxx/go-btree-kv/blob/main/notes/06-storage-comparisons/03-btree-and-lsm.md)），三者互相牵制。要比较两种做法，就要在同一份固定的负载下把它们量出来。性能测量的一般方法（吞吐、延迟分位数、可复现的记录、常见错误）见验证与观测笔记《性能基线》，本篇只讲 LSM 特有的部分。

## 负载与它能看出什么

每种改动只会让某几种负载的数字变化，所以负载要有好几种，各自对着引擎的一条路径。名字沿用 RocksDB 的 `db_bench`。

| 负载 | 做什么 | 能看出什么 | 状态 |
| --- | --- | --- | --- |
| `fillrandom` | 乱序写入 N 个不同的 key，每个一次 | 写吞吐；flush 与 compaction 对前台写入的拖累 | 已实现 |
| `overwrite` | N 次写入，每次随机覆盖一个已有的 key | 写放大、空间放大：旧版本堆积多少、清理要重写多少 | 已实现 |
| `readrandom` | N 次点查，key 存在 | 一次点查要进入几个文件、读几个数据块 | 已实现 |
| `readmissing` | N 次点查，key 不存在 | Bloom filter 的效果 | 已实现 |
| `seekrandom` | 范围扫描：随机挑一个已有的 key 作起点，按顺序读若干条（默认 100）；扫描的次数是 N 除以每次的条数 | 游标与归并的开销，随来源个数增长 | 已实现 |

读负载读的是前面写负载留下的数据，所以一次运行按顺序执行若干种负载，共用同一个库。

默认规模是 key 16 字节、value 100 字节、100 万条，与 `db_bench` 的默认值相同，以后可以和成熟引擎在同一规模下对照。

### 不存在的 key 要落在 key 范围之内

每个 SST 都记着自己的首末 key。如果要查的 key 比库里所有 key 都大，引擎只凭首末 key 就能排除每一个文件，一个数据块也不用读，有没有 Bloom filter 都一样快。

要测出 Bloom filter 的作用，不存在的 key 必须夹在存在的 key 之间。这里的做法是：存在的 key 用偶数编号，不存在的 key 用奇数编号，都写成 16 位十进制。

```
存在：  0000000000000000  0000000000000002  0000000000000004  …
不存在：        0000000000000001  0000000000000003  …
```

### 多线程

`--threads N` 让 N 个线程同时向同一个被测对象发起操作，总操作数不变，平分给各线程。

- 每个线程有自己的随机序列，种子由总种子、负载和线程序号决定，结果仍可复现。
- `fillrandom` 先把全部 key 整体打乱，再切成 N 段分给各线程，保证每个 key 仍然恰好写一次。
- 所有线程先在一条起跑线上等齐，再一起开始计时，避免先启动的线程独占一段时间。
- 每个线程各记各的延迟直方图，结束后合并。吞吐是总操作数除以从起跑到最后一个线程结束的时间。

线程数是比较并发结构时最重要的参数：单线程下看到的是结构本身的快慢，多线程下看到的是线程之间互相挡住多少。

### 同一个种子，同一串操作

随机负载由种子决定。伪随机数算法写在驱动程序里（SplitMix64），不依赖外部库，种子相同，操作序列就逐字节相同；每种负载用自己的随机序列，调换负载的顺序不影响各自访问哪些 key。

## 三种放大怎样取数

| 放大 | 算式 | 分子从哪来 | 分母从哪来 |
| --- | --- | --- | --- |
| 写放大 | 引擎写到磁盘的字节 ÷ 用户写入的字节 | 引擎内部计数：WAL、flush、compaction 三处 | 每次写入的 key 长度加 value 长度 |
| 读放大 | 每次点查进入的 SST 个数；每次点查读的数据块个数 | 引擎内部计数 | 点查次数 |
| 空间放大 | 数据目录的大小 ÷ 有效数据的大小 | 从外面看目录 | 驱动程序算：每个 key 只算最新的一份 |

**写放大和读放大的分子只有引擎自己知道。** 一条记录被 compaction 重写了几遍，一次点查被 Bloom filter 挡掉了几个文件，从外面看不出来。所以引擎从一开始就带一组计数器，每个写文件、读文件的位置都往里累加；功能写完再回头补，要改动每一处读写文件的代码。

计数的位置：

```
put / delete        user_bytes_written      += key 长度 + value 长度
追加 WAL            wal_bytes_written        += 写入的字节
flush 写 SST        flush_bytes_written      += 文件大小
compaction 写 SST   compaction_bytes_written += 文件大小

get                 gets          += 1
进入一个 SST 查找   tables_probed += 1    被 key 范围或 Bloom filter 排除的不算
从文件读一个数据块  blocks_read   += 1    命中 block cache 的不算
```

**用户字节按 key 和 value 的长度算**，不含引擎自己加的长度字段、校验和、索引。这些编码开销正是写放大的一部分，应当留在分子里。

**读放大记两个数。** 进入几个 SST 反映层数与 Bloom filter 的效果；读几个数据块反映真正的 I/O 次数，还受 block cache 影响。两者可以差很多：进入一个 SST 但数据块在缓存里，不产生 I/O。

**空间放大的分母由驱动程序算。** 引擎不知道哪些数据是有效的（知道的话就不需要 compaction 了），而驱动程序知道自己写过哪些 key、每个 key 最新的 value 多大。固定大小的负载下，它就是不同 key 的个数乘以每条记录的大小。

### 读数的时机

compaction 在后台、延后发生，读数太早会漏掉还没做的工作：

- 写放大要等后台的 flush 和 compaction 都停下来再读。写入刚结束时数据多半还在 L0，此时写放大看起来很低，欠下的 compaction 还没算进去。
- 空间放大随时间起伏，compaction 之前高、之后低，记录的只是某一刻的值，要注明是写入刚结束时还是 compaction 停下后。
- 计数器之间互相独立，一次读数里的几个值不保证对应同一时刻。负载结束、后台停下后再读，这个差别就不存在了。

一段负载的数字用前后两次读数相减得到，这样同一次运行里的几种负载各算各的。

## 被测对象

驱动程序通过一个很小的接口（写入、点查、范围扫描）操作被测对象，换一个实现就能在相同负载下对照。目前有三个：

| 名字 | 是什么 | 用来看什么 |
| --- | --- | --- |
| `btreemap` | 一把互斥锁保护的 `BTreeMap`，不写磁盘 | 内存基线："只在内存里维护一张有序表"能有多快 |
| `memtable` | 引擎的单张 memtable（并发跳表） | 有序结构本身的差别 |
| `engine` | 完整的引擎：memtable 写满冻结，后台写成 L0 的 SST（放在临时目录里），读块经过块缓存；`--memtable-mb`、`--block-cache-mb` 设定 memtable 上限与块缓存容量 | 把数据分散到多个来源、写成文件之后，读写各付出什么 |

引擎的数字与内存基线相比，差出来的部分就是分层与持久化的代价。

**每段负载之后等后台做完。** 写入快于落盘时，冻结的表在内存里排队。驱动程序在每段负载计时结束后，等冻结的表全部写成文件，再读计数器、开始下一段：这样写负载的计数器包含它引起的全部 flush，读负载面对的也总是"全部在文件里"的同一种状态。等待的时间单独列出，不计入吞吐。

### 第一组引擎的数字说明了什么

冻结的表还不会落盘时，memtable 的上限直接决定表的张数。同一份负载（100 万条，单线程，见 [结果记录](../bench/results/2026-10-10-engine-and-scan.md)）：

| memtable 上限 | 结束时的表数 | 随机写入（万次每秒） | 点查存在的 key | 点查不存在的 key | 范围扫描（万次每秒，每次 100 条） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单张表，不设上限 | 1 | 136 | 93 | 100 | 4.97 |
| 64 MB | 4 | 181 | 38 | 23 | 1.81 |
| 4 MB | 56 | 386 | 4.2 | 1.6 | 0.62 |

上限调小，每张跳表更小，写入更快；同时表更多，点查要从新到旧逐张去看，查不存在的 key 要看完每一张才能确定。写与读是同一个旋钮的两头，这就是读放大最直接的样子，也是 flush、compaction 和 Bloom filter 各自要解决的问题。

### 写成 SST 之后的数字说明了什么

冻结的表写成 SST、有了块缓存与按 key 范围跳过文件之后（[结果记录](../bench/results/2026-10-14-disk-cache-and-range.md)，30 万条、33 个 SST、单线程）：

- **读放大要看两个数。** 乱序写入时文件范围互相重叠，点查平均进入 17 个 SST，查不存在的 key 进入全部 33 个；块缓存放得下全部数据时，从文件读的块几乎为 0，吞吐提高 2.8 倍，但进入的 SST 个数不变。前者由文件的组织决定，后者由缓存决定。
- **文件范围不重叠时，每次点查只进入一个文件**，点查快 14 倍、查不存在的 key 快 29 倍。这就是 compaction 之后各层的样子，也是 Bloom filter 要在重叠的文件上补回的部分。
- **缓存只放得下一部分时收益很小。** 数据都在页缓存里时，没命中的代价只是一次系统调用加解码，约 1 微秒；放入与淘汰的开销抵消了大半收益。块缓存的价值要在数据大于内存时才显出来，这组数字没有覆盖。
- **写放大目前约 1.05**，只来自 flush 的编码开销；有了 compaction 和 WAL 之后才会明显上升。

## 本项目的做法

本仓库是一个 cargo workspace，引擎与驱动程序是两个 crate：

| crate | 目录 | 内容 |
| --- | --- | --- |
| `lsm` | [engine](../engine/src/lib.rs) | 引擎。`Stats` 是一组原子计数器，`snapshot` 读出一份普通数值，`since` 求两次读数之差 |
| `lsm-bench` | [bench](../bench/src/main.rs) | 驱动程序：生成负载、逐个操作计时、打印 Markdown 报告 |

驱动程序不放进引擎的单元测试：测试要快、要确定，基准要跑得久、数据量大，并且必须用 release 编译。

计数器用原子类型，各自以 `Relaxed` 递增：它们之间没有需要同时成立的关系，只要每次加法不丢。内存序的含义见 Rust 笔记《原子内存序》。

随功能加入的记录点：

| 时机 | 要记的对比 |
| --- | --- |
| 写路径完成（flush 到 L0） | 第一份端到端基线，与内存基线对照 |
| Bloom filter 前后 | `readmissing` 的吞吐、每次点查进入的 SST 个数 |
| 三种 compaction 策略 | 同一份 `overwrite` 负载下的写放大、空间放大、读放大 |
| WAL 的同步策略 | 每次写入都同步与批量同步的写吞吐和延迟分位数 |

## 与 B+Tree 的对应

放大不是 LSM 独有的，只是来源不同。

| | CoW B+Tree | LSM |
| --- | --- | --- |
| 写放大的来源 | 改一条记录要重写从叶子到根的每一页。树高 3、页 4 KB 时，改一条一百多字节的记录写出约 12 KB，再加 meta 页；同一批里的多条记录可以分摊同一批页 | 一条记录被 flush 写一次，之后每下沉一层被 compaction 重写一次或多次，另加 WAL |
| 读放大的来源 | 从根到叶子一条路径，页数等于树高 | 一个 key 可能要查多个来源，靠 key 范围、Bloom filter 减少 |
| 空间放大的来源 | 页内的空闲空间；等待读者结束才能回收的旧页 | 被覆盖的旧版本与墓碑，等 compaction 才清理 |
| 写入发生的时刻 | 全部在提交时，前台承担 | 大部分推迟到后台，前台只写 WAL 和内存 |

LSM 把写入的大部分代价挪到了后台，所以量它的时候必须把后台的工作算进来，这也是读数时机那一节的由来。页回收见存储笔记[页回收与读者](https://github.com/luckysxx/go-btree-kv/blob/main/notes/05-storage-recovery/07-page-reclamation-and-readers.md)。

- **RocksDB `db_bench`**：负载名（`fillseq`、`fillrandom`、`overwrite`、`readrandom`、`readmissing`、`seekrandom`、`readwhilewriting` 等）与默认规模（key 16 字节、value 100 字节、100 万条）的出处。RocksDB 自己的统计输出里按层列出写放大。

## 常见错误

- **不存在的 key 落在 key 范围之外。** 靠首末 key 就全部排除，量不出 Bloom filter。
- **写放大读数太早。** 后台的 compaction 还没做完，数字偏低。
- **只算 SST，不算 WAL。** 每条记录至少还在 WAL 里写了一遍。
- **数据量太小。** 全部数据还在 memtable 里，没有触发过 flush，量到的是内存表而不是 LSM。
- **用引擎编码后的大小当用户字节。** 编码开销被从分子挪到了分母，写放大被低估。

## 位置

仍是[全景](README.md#全景)的第 ⑤ 步，compaction 这组的最后一篇。[L09](09-compaction-execution.md) 写了合并的执行，[L10](10-simple-leveled-compaction.md) 的简单分层与 [L11](11-tiered-compaction.md) 的 tiered 是两种决策；这一篇是 RocksDB 默认用的 leveled：保留"每层一个 sorted run"，但按字节定每层的目标、从最底层往上建层、每次只合并一小段。执行的骨架照用。下一篇 [L13](13-manifest.md) 开始补重启：manifest 记下每一层有哪些文件。

## 与 B+Tree 阶段的对应

| B+Tree | LSM（leveled） |
| --- | --- |
| 树从根往上长：根满了分裂，上面加一层新根，叶子始终在最底层 | 层从最底层往上启用：最底层大到一定程度，才在它上面启用一层；数据最终都在最底层 |
| 一次插入只改动一条路径上的几页，代价与树的大小无关 | 一次部分合并只改动一个文件与下层的一小段 key 范围，单个任务的大小与数据库的大小无关 |
| 页满了才分裂，各页的大小靠"满"这一条规则维持 | 层超过目标才往下推，各层的大小靠目标与分数维持 |

## 问题：简单分层的三处粗糙

简单分层（L10）能用，但有三处浪费或不准：

| 简单分层的做法 | 带来的问题 | leveled 的改法 |
| --- | --- | --- |
| 比较文件数 | 文件大小不一时比例失真 | 按**字节**比较 |
| 上层整层并进下层 | 输入与输出同时在盘上，峰值空间接近翻倍；单个任务很长，期间 L0 积压 | **部分合并**：上层只挑一个文件，下层只拉进与它重叠的文件 |
| 从 L1 开始一层层往下填 | 新数据要一层层原样复制才沉到最底层（[穿过空层的复制](10-simple-leveled-compaction.md#浪费穿过空层的复制)） | **从最底层往上建层**，L0 直接并进"基准层" |

另一个方向是 tiered（L11）：放松"每层一个 sorted run"，写得少，读与空间付出代价。leveled 走的是保留这条规矩、把执行做细的路。

## 目标大小：从最底层往上算

每层有一个**目标大小**：这一层应该最多放多少字节。计算只看最底层的实际大小：

- 最底层的目标 = max(最底层的实际大小, `base_level_size`)。
- 从倒数第二层往上：下一层的目标**超过** `base_level_size` 时，这一层的目标 = 下一层的目标 ÷ `level_size_multiplier`；否则是 0，再往上也都是 0。

第一个目标大于 0 的层叫**基准层**（base level），L0 总是并进它。以 multiplier 10、`base_level_size` 16 MB、L0 之下 4 层为例：

| 最底层的实际大小 | L1 | L2 | L3 | L4（最底） | 基准层 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 8 MB | 0 | 0 | 0 | 16 MB | L4 |
| 116 MB | 0 | 0 | 11.6 MB | 116 MB | L3 |
| 1.6 GB | 0 | 16 MB | 160 MB | 1.6 GB | L2 |
| 2 GB | 2 MB | 20 MB | 200 MB | 2 GB | L1 |

数据少时 L0 直接并进最底层；最底层超过 `base_level_size` 才在它上面启用一层缓冲；那一层的目标也超过时再往上启用一层。中间层出现时下面已经有数据，层间合并从一开始就是真正的合并，不会往空层原样复制。这就是 RocksDB 的 `level_compaction_dynamic_level_bytes`。

### `base_level_size` 是什么

它不是哪一层的固定大小，而是一条线：**L0 每次并进去的那一层大约不超过这么大。** 它只出现在"要不要再往上启用一层"的判断里；除最底层（数据少时取它的值）以外，每层的目标要么是下一层的 1/multiplier，要么是 0。结果是基准层的目标总在 `base_level_size` 以内，"最多只有一层的目标不超过它"。

取多大：L0 每次往下并，读写的量大约是"L0 攒下的几个文件 + 基准层"。基准层与 L0 一次攒下的量差不多时，这一步的写放大约为 2。所以 RocksDB 建议取"memtable 大小 × L0 触发值"，它的默认值 256 MB 就是 64 MB × 4。取得过大（远大于数据），整个数据库只有最底层在用，L0 每次都并进最底层，退化成全量合并。

### 为什么不从上往下算

另一种做法是从上往下定死：L1 是 `base_level_size`，L2 是它的 multiplier 倍……这是 RocksDB 以前的默认做法，最底层"剩下多少算多少"。两个问题：

- **穿过空层的复制。** 数据从 L1 往下填，每层第一次满了往下并时，下面一层是空的，只是原样复制。
- **空间放大没有上限。** 设 L1 16 MB、L2 160 MB、L3 1.6 GB，数据共 200 MB：形状是 L1 16 MB、L2 160 MB、L3 24 MB，最底层比上一层还小。被覆盖的旧版本要等新版本沉到它所在的层才丢掉，上面的层装的往往正是下面数据的新版本；上面几层合起来比最底层大时，最坏一半以上的字节是旧版本，空间放大接近 2。从下往上算时最底层总约占九成（上面各层合起来约是它的 1/10 + 1/100 + … ≈ 0.11），空间放大最多约 1.11。

### 目标是软的

目标大小本身不限制什么，管它的是下一节的分数：超过目标就排进待做的合并。两次合并之间、或者合并跟不上写入时，一层可以暂时超过目标；一层比目标少很多也没人管。最底层的目标取的是实际大小与基准大小中较大的，分数永远不超过 1，它下面没有地方可推，数据最终就待在这里。RocksDB 里对应的函数叫 `MaxBytesForLevel`，名字说的是上限，用法相同。

## 优先级

1. L0 的文件数达到 `level0_file_num_compaction_trigger`：L0 全部并进基准层；基准层上面若有数据的层，并进其中最靠上的那个。L0 的文件读的时候要逐个看，排在最前。
2. 否则 L1 到倒数第二层，每层的**分数** = 实际大小 ÷ 目标大小，只有大于 1 的可以选；取分数最大的那层 n，并进 n + 1。分数相同时取上面的层。
3. 目标是 0 却有数据的层（数据变少、基准层下移之后留下的）分数算作无穷大，最先往下推；目标是 0、也没有数据的层不选。
4. 最底层没有下一层，不参加。

第 1 条的后半句守的是读路径的不变量：**越靠上的层越新。** 基准层上面有数据，有两种来历：删除让最底层变小、基准层下移之后留下的；从按层号往下填的策略（简单分层）换成 leveled 打开的。这时把 L0 并进基准层，L0 里一个 key 的新值落到了下面，上面那层里的旧值还在，点查从上往下先查到旧值。RocksDB 算基准层时也不让它低于第一个非空的层（`VersionStorageInfo::CalculateBaseBytes` 里的 `first_non_empty_level`）。

每个任务做完都要重新算目标与分数：一次合并改变了各层的大小，常常让下一层也超过目标。反复要任务总会停下：每个任务都把至少一个文件往下移一层。

## 部分合并

**上层是 Ln（n ≥ 1）**：只挑一个文件，再找出下层所有与它 key 范围重叠的文件（两端都算，首末 key 相等也算重叠：那个 key 两个文件里都有）。只有这几个文件参加合并，结果放回下层，下层其余的文件不动。

**上层是 L0**：拿全部 L0 文件。L0 的文件之间有新旧之分，读的时候先看 L0、再看基准层；只把较新的文件推下去、留下与它重叠的较旧文件，读的时候会先在 L0 读到旧值：

```
L0：  [新 X: a=2]   [旧 Y: a=1]
只把 X 推进基准层之后：
L0：  [旧 Y: a=1]       基准层：[a=2]
读 a：先看 L0，读到 Y 里的 a=1，错了
```

所以挑 L0 时，挑了某个文件，所有比它旧并且与它重叠的文件都必须一起挑；最简单又一定正确的是全部拿走。随机 key 下每个 L0 文件都覆盖几乎整个 key 范围，挑一部分与挑全部没有差别。合并期间新 flush 的文件比任务里的都新，留在 L0 是对的。

**重叠按整体跨度算**：上层有好几个文件时（L0），下层要找的是与"全部上层文件的最小首 key 到最大末 key"重叠的文件，不能一个文件一个文件地比：

```
L0：   [1─10]           [50─60]
基准层：         [20─30]
逐个比较：[20─30] 跟哪个都不重叠，留下
但输出按大小切分，可能切出一个 [1 ─── 55] 的文件，盖住 [20─30]，同一层出现重叠
```

**部分合并省的是什么**：随机写入下，上层的一个文件大约与下层 multiplier 个文件重叠，平摊下来写的字节与整层合并差不多。它省的是**峰值空间**（同时在盘上的输入与输出只有一个文件加一小段下层，而不是整层）和**单个任务的时长**（与数据库的大小无关；整层合并在数据大时要很久，期间 L0 一直积压）。

### 挑哪个文件

同一层的文件大小相近（都按 `target_sst_size` 切），挑法真正的区别是挑哪一段 key 范围。成本是"这个文件加上下层与它重叠的文件全部重写"，收益是"这个文件的字节往下移了一层"。RocksDB 的 `compaction_pri` 有几种：

| 挑法 | 照顾什么 |
| --- | --- |
| 编号最小（在这一层待得最久，mini-lsm 的做法） | 公平：每段 key 范围早晚都会被推下去，墓碑最终到达最底层被丢掉 |
| 下层重叠字节 ÷ 自身大小最小（RocksDB 现在的默认） | 每往下移 1 字节重写得最少，直接压低写放大 |
| 墓碑多的优先（按"补偿后的大小"） | 尽快回收被删除数据的空间 |
| 按 key 轮转（round-robin） | 每段范围轮流做，写放大与按时间挑差不多，但更可预测 |

key 均匀随机时，各文件与下层的重叠都差不多，几种挑法结果接近；写入不均匀（一部分 key 前缀写得多）时，"重叠最小"会优先推那些推起来便宜的范围。

## 换状态：拿掉输入，整块插入

换状态时上层按编号拿掉输入（L0 里合并期间新 flush 的文件留下），下层按编号拿掉参加合并的文件，再把输出插进下层。输出可以**整块**插进一个位置，不需要整层重新排序：

- 输出的范围就是全部输入的范围拼起来。
- 留下的下层文件与上层输入不重叠（否则会被选中），与被拿掉的下层文件也不重叠（同一层本来就互不重叠）。
- 所以输出范围里的每一处原来都被输入占着，留下的文件全在它的左边或右边。

```
上层挑的文件：   [100 ────────── 200]
下层：  [50─90]      [120─150]          [260─300]
拿掉 [120─150]，输出的范围是 [100─200]，整块插在 [50─90] 与 [260─300] 之间
```

位置用"第一个首 key 不小于输出首 key 的文件"找（`partition_point`），再用 `splice` 插入。也可以像 mini-lsm 那样把输出与留下的文件拼在一起按首 key 排序，结果一样；但排序会把"其实重叠了"的错误盖住：排好序的重叠文件看起来完全正常。插入之后检查下层仍是一个 sorted run（相邻两个的前一个末 key 严格小于后一个首 key），策略漏挑了重叠的文件时当场发现。

## trivial move

上层挑出的文件与下层**没有任何重叠**时，合并不会去掉任何东西，只是原样重写。这时可以不读写文件，只在状态里把文件从上层挪到下层，叫 trivial move。条件：

- 下层没有与上层文件的整体范围重叠的文件；
- 上层的文件按首 key 排好之后彼此不重叠（只有一个文件时自然成立）。

第二条让几个 L0 文件也能一起挪：它们彼此不重叠，说明没有一个 key 同时在两个文件里，新旧无关紧要，排好就是一个 sorted run。顺序写入时这种情况很多：每个 flush 出的文件都在前一个的右边。第一条按整体范围判断，挪进下层时也一定能整块插入，不会夹住下层的某个文件。

几点细节：

- **挪动的文件不能删**：它还在状态里。执行时要跳过"同步目录"与"删旧文件"两步。
- **挪进最底层时墓碑留下**：合并进最底层会丢墓碑，挪动不读内容，墓碑原样进了最底层。读的结果不受影响，只是暂时多占空间，以后它所在的范围再被合并时丢掉。
- **文件编号不变**，块缓存里按编号存的块继续有效。
- **判断放在策略里**：任务带一个"只挪动"的标记，执行看到它只换状态。能不能挪只看各文件的范围，是策略本来就在算的东西；执行最危险的一步是删旧文件，任务上的标记让"不删"与"不写"看的是同一个事实。
- **挪进下层时按 key 排好**：L0 的列表是新的在前，不是按 key 排的。任务里的文件列表保持状态里的顺序（合并时归并靠这个顺序决定谁更新），只在挪进下层这一步现排一个按首 key 排好的副本，而不是让同一个字段在"合并"与"挪动"两种任务里各有一种顺序。

L0 的文件为什么常常不止一个：后台线程不是每次 flush 之后立刻醒来。写入快的时候，线程醒来时 L0 已经积了好几个文件。只允许挪单个文件的话，顺序写入下 L0 的任务几乎都要原样复制一遍。

## 写放大从哪里来

稳定时，一条数据从基准层往下每推一层，要陪着重写下层约 multiplier 倍的数据：上层一个文件与下层约 multiplier 个文件重叠。粗算：

- 写放大 ≈ 1（flush）+ 约 2（L0 并进基准层）+ （层数 − 1）× multiplier
- 层数 ≈ log_multiplier(数据量 ÷ 基准大小) + 1

这是 leveled 保持"每层一个 sorted run"的代价，与 [L11](11-tiered-compaction.md#问题leveled-写得太多) 里的估算一致：调小 multiplier 能降低每层的代价，但层数会变多。部分合并改变的是峰值空间与任务的粒度，不是这个乘积。

基准里的写放大比这个估算低，是因为写入比合并快：L0 积压时合并每次拿到一大批文件，基准层一下子大大超过目标，往下推的时候与下层重叠的比例也变了。基准测的是"全速写完、再等合并追上"，不是合并完全跟得上时的稳定状态。

## 本项目的做法

- **策略**：[compaction/leveled.rs](../engine/src/compaction/leveled.rs)。`LeveledOptions` 三个参数：`level0_file_num_compaction_trigger`、`level_size_multiplier`、`base_level_size_bytes`（字节，`u64`，与 `SsTable::file_size` 一致），`check_options` 断言前两个至少为 1、2，基准至少 1 字节。决策分三个纯函数：`target_sizes`（只看最底层，下一层的目标不超过基准时停下）、`base_level`（第一个大于 0 的目标，返回层号）、`pick_levels`（L0 优先，否则分数最大，分数用浮点数；目标为 0 且有数据时直接返回）。`generate_task` 算出各层的字节数，再交给 `build_task` 挑具体的文件：`pick_upper_sst` 取编号最小的，`key_span` 取整体范围，`find_overlapping` 按两端都包含找重叠。
- **任务**：`LeveledTask { upper_level, upper_ssts, lower_level, lower_ssts, is_lower_level_bottom, is_trivial_move }`，字段沿用简单分层的写法，多一个挪动的标记。
- **两边共用的小工具**：[compaction.rs](../engine/src/compaction.rs) 的 `is_sorted_run`（策略判断能不能一起挪，执行检查换状态之后的层）与 `sorted_by_first_key`（按首 key 排好的副本；排序用 `sort_by`，`sort_by_key` 的闭包不能返回从元素里借出的 `&[u8]`）。
- **执行**：写新文件与简单分层共用 `merge_upper_into_lower`（上层是 L0 时归并，是 Ln 时串接；下层串接）。`run_leveled_task` 先看挪动的标记：挪动时直接换状态；否则写新文件 → 同步目录 → 换状态 → 删旧文件。`apply_leveled_result` 用 `remove_compacted_ssts` 拿掉上层与下层的输入（按编号，个数不对时 panic；全量合并与简单分层拿掉 L0 输入时也用它），再用 `partition_point` 与 `splice` 整块插入，最后断言下层是一个 sorted run。简单分层的 Ln 与 tiered 仍用 `same_ssts`：它们的输入是整层或连续的几个 tier，要求"完全一样"，比"都还在"更严。
- **选项与入口**：`CompactionOptions::Leveled(LeveledOptions)`；`compact_once`、`has_pending_compaction` 各多一个分支，没有换成 trait（见下面的"分支还是 trait"）。全量合并、flush、打开时的形状都与简单分层相同。状态多了只读的 `LsmStorageState::level_at(n)`。
- **对外**：基准驱动 `--compaction leveled`、`--level-multiplier`（默认 10）、`--base-level-mb`（默认取 memtable 上限 × L0 触发值）；命令行程序第三个参数可以是 `leveled`（触发值 2、比例 4、基准约 2 张 memtable，写几百条就能看到中间层从下往上启用）。
- **测试**：策略的目标大小、基准层、选层按例子测，另有"最多一层的目标不超过基准"的性质检查；挑文件测端点相等、整体跨度夹着下层文件、挑最旧、几种挪动与不能挪动的情形、按字节而不是文件数；执行测 L0 与层间任务只换掉重叠的文件、空输出、挪动插在两端与中间、四种断言的失败信息、`compact_once` 挪动时一个字节都不写；两组随机多轮对照 `BTreeMap` 模型（基准层一直是最底层；多层都在用）；`Db` 层测多线程写入时后台按 leveled 合并不丢数据。

### 分支还是 trait

加了第三种策略，`CompactionOptions` 仍是枚举加 `match`：引擎里只多两个分支。trait 能省掉 `match` 的前提是各种策略的任务长得一样，执行只写一套：RocksDB 就是这样，任务统一表示成"各层输入了哪些文件、输出到哪层"，只有挑任务的部分是虚函数（`CompactionPicker`）。这里三种任务换状态的方式各不相同（整层替换、`splice` 换几个 tier、拿掉几个文件再插入），换成 trait，执行这边仍要按任务的类型分开写。策略再多、或者任务统一成一种形状时再换。

### L0 单独放的代价

L0 放在 `l0_sstables`、L1 往下放在 `levels`，写代码时常要分开处理。把这些分支逐个看：L0 用归并、Ln 用串接（文件是否重叠），L0 拿全部、Ln 挑一个（正确性），L0 按编号拿掉（flush 会同时往 L0 加文件），这些都来自 L0 本身的不同，换成 `levels[0]` 也省不掉。真正因为"两个字段"多出来的只有"先选出是哪个 `Vec`"那一两行。分开存的好处是忘了特殊处理时会越界或编译不过；放在一起（LevelDB、RocksDB 的 `files_[0]`）层号就是下标、不用减 1，但忘了 `if level == 0` 时是悄悄读错。

## 效果

[2026-10-19 的基准](../bench/results/2026-10-19-leveled-compaction.md)（与 L10、L11 同一组负载，同一天重跑对照组；leveled 用触发值 2、multiplier 10、基准 8 MB）：

| | 整次运行的写放大 | 写完后等后台 | 停下时空间放大 | 扫描（万次/秒） | 顺序写入的写放大 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 简单分层，4 层 | 5.32 | 1.10 s | 0.98 | 12.2 | 6.10 |
| 简单分层，2 层 | 4.00 | 0.75 s | 0.98 | 11.9 | — |
| leveled，4 层 | 4.32 | 0.82 s | 1.03 | 9.2 | 0.95 |
| leveled，2 层 | 4.39 | 0.85 s | 0.98 | 10.6 | — |
| tiered，`num_tiers` 8 | 2.40 | 0.32 s | 1.34 | 7.1 | 1.90 |

- **穿过空层的复制消失了**：leveled 设 4 层与 2 层一样，简单分层 4 层比 2 层多写约 1.3。
- **写放大介于简单分层与 tiered 之间**，但比只设 2 层的简单分层略高：基准层一直保持在下一层的约 1/10，每往下推一层约重写 multiplier 倍；简单分层在全速写入下整批合并到最底层，反而少写。
- **读与空间接近简单分层**：点查相同；扫描慢一到两成，因为停下时有两三个 sorted run（这是 leveled 的正常形状）。
- **顺序写入**：只允许挪单个文件时写放大是 1.87，多出的部分来自 L0 积压的几个互不重叠的文件被原样复制；允许它们一起挪之后降到 0.95，compaction 一个字节都没写。
- **一千万条（约 1.16 GB）**：排序与差距不变（简单分层 5.88、leveled 4.88、tiered 2.67），leveled 用上了三层，形状是 3 / 26 / 265 个文件的 10 倍阶梯。

## 工业对照

**mini-lsm**（[leveled.rs](https://github.com/skyzh/mini-lsm/blob/v202608/mini-lsm/src/compact/leveled.rs)）：规则相同。不同处：任务里记文件编号，状态里有"编号 → 文件"的表；分数用浮点数，排序后取最大；L0 的任务拿全部 L0；换状态时把输出与留下的文件拼起来按首 key 排序，manifest 重放时文件还没打开、拿不到首 key，所以那时先不排（`in_recovery`）；没有 trivial move（列为加分项）；层数是策略参数。

**RocksDB**：

- `level_compaction_dynamic_level_bytes` 就是从最底层往上算目标，较新的版本默认开启；`max_bytes_for_level_base` 默认 256 MB、`max_bytes_for_level_multiplier` 默认 10。
- 每层一个分数：L0 主要看文件数 ÷ 触发值（默认 4），L1 往下是字节数 ÷ 目标；分数大于等于 1 的需要合并，先做最高的。另有优先项：墓碑多的文件、太久没合并的文件（TTL、periodic compaction）。
- 挑文件的 `compaction_pri` 默认是"下层重叠字节 ÷ 自身大小最小"；挑中后会把输入扩展到完整的 key 边界，避免同一个 key 的不同版本被切在两个任务里。
- trivial move：输入与输出层不重叠时只改元数据；挑 L0 任务时也会尝试把几个彼此不重叠的 L0 文件一起挪下去。
- 写入停顿：L0 到 20 个文件减速、36 个停止；待做的合并字节数太多时也会减速。

**GreptimeDB mito2**：只有两层（L0 与 L1），按时间窗口组织（TWCS，见 [L11 的导读](11-tiered-compaction.md#导读mito2-的-twcs-怎样找-sorted-run)），没有多层的目标大小与基准层，对照意义不大。时序数据大多按时间追加，与这里"顺序写入下 trivial move 能省掉全部合并"是同一类负载。

## 常见错误

- **目标从上往下定死。** 数据从 L1 一层层往空层复制；数据量不合适时最底层比上一层还小，空间放大接近 2。
- **把 `base_level_size` 当成基准层的固定目标。** 基准层的目标是下一层的 1/multiplier，`base_level_size` 只决定什么时候再往上启用一层。
- **基准大小取得远大于数据。** 只有最底层在用，L0 每次都并进最底层，等于全量合并。
- **L0 只挑较新的一部分文件推下去。** 留在 L0 的较旧文件先被读到，读到旧值。
- **L0 总是并进基准层，跳过基准层上面有数据的层。** L0 的新值落到旧值下面，点查读到旧值。只写不删、也不换策略时基准层只会往上走，测不出来。
- **下层的重叠逐个文件比，而不是按上层的整体跨度。** 输出跨过 L0 文件之间的空隙，盖住留下的下层文件，同一层出现重叠。
- **端点相等当成不重叠。** 那个 key 两个文件里都有，留下的那个版本可能是旧的，同一层出现重叠。
- **换状态时把输出接在下层最后，或者整层排序。** 前者下层乱序；后者把漏挑重叠文件的错误掩盖掉。
- **分数等于 1 也往下推，或者目标为 0 时做除法不处理。** 前者合并停不下来或过于频繁；后者 0 ÷ 0 是 NaN，有数据的层被漏掉或误选。
- **trivial move 之后删了文件。** 状态里还引用着它，之后读到不存在的文件。
- **几个 L0 文件一起挪时没有按 key 排好。** L0 是新的在前，原样插进下层就乱了序。
- **最底层也参加打分。** 没有下一层可推，越界或空转。

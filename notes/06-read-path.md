## 状态里多了什么

引擎的状态原先是"一张可写的 memtable 加若干张冻结的 memtable"，现在多一个列表：L0 的 SST，新的在前。L0 的文件各自来自一次 flush，彼此的 key 范围可以重叠，所以读的时候每个都要看。

新旧的顺序因此有三段：可写的 memtable 最新，其次是冻结的 memtable（新的在前），最后是 L0 的 SST（新的在前）。

## 点查

从新到旧依次找，遇到这个 key 的记录就停，不论它是值还是墓碑：

```
可写的 memtable → 冻结的 memtable（逐张）→ L0 的 SST（逐个）
```

在一个 SST 里查一个 key：定位到第一条大于等于它的记录，再看那条记录的 key 是否恰好相等。相等才算这个 SST 里有；不相等或者游标无效，说明这个 SST 里没有，接着看更旧的。

墓碑的处理与 memtable 相同：读到墓碑就返回"不存在"，不能当作没看见继续往更旧的来源里找，否则被删除的值会复活。

查到 SST 要读磁盘，所以点查从这一篇起可能失败。

## 范围扫描：两路归并

扫描要把所有来源归并成一个有序的结果。来源现在有两种类型：memtable 的游标与 SST 的游标。[多路归并](03-iterators-and-merge.md#多路归并) 用堆，堆里的元素必须是同一种类型，所以分两层：

```
去墓碑、到上界为止
      ↑
两路归并            两个可以不同类型的游标合成一个；同一个 key 取前一个的
   ↑        ↑
多路归并    多路归并
memtable   SST
的游标      的游标
```

只有两个来源时不需要堆，每一步直接比较两边当前的 key：

```
创建、每次前进之后，做两件事：
    两边当前的 key 相同 → 让后一个（旧的）前进一步
    决定当前用哪一边：只有一边有效就用它；两边都有效用 key 小的
前进：
    让给出当前记录的那一边前进，然后重做上面两件事
```

"key 相同时让旧的一边前进"与多路归并里清理旧版本是同一件事。每个来源里同一个 key 至多一条，所以跳一步就够，跳完之后两边的 key 一定不同，选哪一边不会出现相等的情况。

把前一个位置给 memtable 那一组，因为它比任何 SST 都新。两个位置的类型不同，写反了无法通过编译。

## 范围的两端

**下界**在建立每个来源的游标时处理。memtable 的游标本来就接受一个范围。SST 的游标只有"定位到第一条大于等于某个 key 的记录"一种操作，三种下界分别是：

| 下界 | 做法 |
| --- | --- |
| 包含 k | 定位到 k |
| 不包含 k | 定位到 k；停下的那条恰好等于 k 时，再前进一步 |
| 没有下界 | 从第一条开始 |

**上界**放在最外层统一处理。memtable 的游标自己会在上界处停下，SST 的游标不会，它只管一直往后走。最外层每次检查里面那层当前的 key 是否越过了上界；key 是递增的，一旦越过，之后的也都在范围外，游标就此无效。

去墓碑与上界要一起考虑：跳过墓碑的循环也要在上界处停下，否则范围内最后几条恰好是墓碑时，会一路跳到范围之外，把那里的一条记录当作结果给出去。

## 读放大

到这里，一次点查最坏要看全部的 memtable 和全部的 L0 文件，每个文件至少读一个块；一次扫描要在每个来源上各放一个游标。这就是读放大，文件越多越严重。有三样东西减少它：每个 SST 的首末 key 可以排除范围不相交的文件（下一节）；Bloom filter 可以排除不含某个 key 的文件（[Bloom filter](08-bloom-filter-and-prefix-compression.md)）；compaction 减少文件的个数并让层内的范围不重叠（[compaction](09-compaction-execution.md)）。

## 按 key 范围排除文件

每个 SST 打开时就从索引里得到了首 key 与末 key，它们一直在内存里。用它们做判断不碰磁盘：

- **点查**：key 不在 `[首 key, 末 key]` 里，这个文件一定没有它，跳过，接着看更旧的文件。落在范围里也不一定有，它可能在两条记录之间（Bloom filter 回答的正是这种情况）。
- **扫描**：范围与 `[首 key, 末 key]` 没有交集，就不为这个文件建游标；建游标本身要读它的一个块。

两个区间相交，等价于"一方的起点不在另一方的终点之后"：范围的下界不在末 key 之后，并且范围的上界不在首 key 之前。端点是否包含要分开处理：下界包含时恰好等于末 key 也算相交，不包含时不算；上界同理，比较的对象是首 key。不设限的一端永远满足。

效果取决于文件之间的范围重叠得多不多。L0 的每个文件是一段时间里的写入：写入的 key 随机时，每个文件都几乎覆盖整个 key 空间，几乎排除不了；key 随时间递增（自增 id、时间戳）时，文件之间几乎不重叠，大部分都能排除。compaction 之后，同一层的文件互不重叠，这个判断加上二分就能直接找到唯一可能的文件。

实测（[结果记录](../bench/results/2026-10-14-disk-cache-and-range.md)）：33 个 SST，乱序写入时点查平均进入 17 个、查不存在的 key 进入全部 33 个；按 key 顺序写入时都只进入 1 个，点查快 14 倍，查不存在的 key 快 29 倍。

本项目的实现是 `SsTable::may_contain_key` 与 `SsTable::overlaps_range`，在 `get` 与 `scan` 遍历 L0 时调用。测试借块缓存观察有没有读文件：每个测试文件只有一个块，缓存里的块数就是读过的文件数。

工业对照：mini-lsm 写成独立的函数 `key_within` 与 `range_overlap`。GreptimeDB mito2 是时序引擎，数据大致按时间先后写入，按每个文件的时间范围排除文件（`src/mito2/src/read/scan_region.rs` 的 `file_in_range`），比较的维度从 key 换成了时间。

## 常见错误

- **点查时遇到范围之外的文件就 `break`。** L0 的文件范围互相重叠、也不按 key 排列，这个文件不可能有，不代表更旧的文件里也没有。
- **只检查一端。** 只比较首 key 时，排除不了 key 比末 key 还大的文件，反过来也一样；结果仍然正确，只是白读了块，正确性测试发现不了，要看读了几个块。
- **范围的下界去和首 key 比、上界去和末 key 比。** 两个区间相交的条件是交叉比较：下界对末 key，上界对首 key。
- **包含与不包含的端点用了同一种比较。** 恰好碰到端点时判断错：把相交的文件排除了，会漏掉记录；把不相交的留下，只是白读一个块。
- **在 SST 里定位之后不比较 key 是否相等。** 把"第一条更大的记录"当成了要找的 key，查一个不存在的 key 会得到别的 key 的值。
- **SST 里读到墓碑时接着往更旧的文件里找。** 被删除的值复活。
- **L0 的文件从旧到新查，或者交给归并时顺序颠倒。** 旧值盖住新值。
- **两路归并里 key 相同时没有让旧的一边前进。** 同一个 key 输出两次，第二次是旧值。
- **两路归并前进之后没有重新决定用哪一边。** 一直从同一边取，结果不再有序。
- **不包含下界时无条件多走一步。** 下界不在文件里时，定位停下的那条本来就是范围内的第一条，多走一步就把它漏掉了。
- **SST 的数据没有经过上界的检查。** 扫描越过范围一直读到文件末尾。

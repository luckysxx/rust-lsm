# memtable 与跳表

状态：部分已整理 · 代码：[mem_table.rs](../engine/src/mem_table.rs) 的 `MemTable`；[lsm_storage.rs](../engine/src/lsm_storage.rs) 的 `LsmStorageState`、`LsmStorage`

## 问题

LSM 把写入先攒在内存里，攒够一批再顺序写成一个文件（为什么这样比逐条改页便宜，见 [B+Tree 也可以把写入攒在内存里](../../storage/notes/06-storage-comparisons/03-btree-and-lsm.md#btree-也可以把写入攒在内存里)）。攒写入的那张内存表就是 memtable。它要满足：

- `put(key, value)` 与 `get(key)`，key 和 value 是任意字节串。
- 能按 key 的顺序遍历。
- 多个线程同时读写。
- 能表示一个 key 已被删除。
- 知道自己大概多大，引擎据此决定何时把它冻结并刷成 SST。

## 为什么内存里就要有序

平时无序、刷盘时再排序是不够的，有三处需要顺序：

- 写出的 SST 必须有序，才能二分查找、才能与别的文件归并。
- 范围扫描要读它：最新的数据只在 memtable 里，扫描必须能按顺序取出落在范围内的 key。
- 点查也要读它：一条刚写入的记录在刷盘之前只存在于这里。

后两条要求它在任何时刻都是一张有序、可查找的表。

## 为什么并发成了问题

CoW B+Tree 没有这个问题：只有一个写者，读者读的是已提交的旧页，写者写的是新页，读写碰不到同一块内存（见 [单机 KV API](../../storage/notes/05-storage-recovery/08-single-node-kv-api.md)）。memtable 两条都不成立：

- 读写碰的是同一个结构。写入一完成就要对读者可见，没有"提交后才发布"这一步；读者遍历到一半时，写者可能正在插入。
- 前台写入只是追加日志加改内存，本身很便宜，所有写线程都挤在 memtable 上。只允许一个写者就浪费了多核。

所以需要一种能在有人遍历的同时让多个线程插入的有序结构。

## 候选结构

| 结构 | 问题 |
| --- | --- |
| 有序数组 | 插入要挪动后面所有元素 |
| 平衡树加一把互斥锁 | 所有读写排队 |
| 平衡树加一把读写锁 | 任何一次写入挡住全部读者 |
| 平衡树加细粒度的锁 | 插入可能引发分裂或旋转，改动沿路径向上传播，一次插入牵涉哪些节点事先不知道，加锁很复杂 |
| 跳表 | 费内存、缓存局部性差，但插入是局部的 |

## 跳表

从有序链表出发：插入只改两个指针，但查找要从头逐个走。跳表给链表加上逐层变稀的"快车道"，每个节点有一个随机的高度，高的节点同时出现在上面几层的链表里。

```
第 3 层  头 ─────────────────────────→ 30 ─────────────→ 尾
第 2 层  头 ─────────→ 10 ───────────→ 30 ─────────────→ 尾
第 1 层  头 ───→  5 ─→ 10 ───→ 20 ───→ 30 ───→ 40 ─────→ 尾
第 0 层  头 → 3 → 5 → 10 → 15 → 20 → 25 → 30 → 35 → 40 → 尾
```

- **查找**：从最高层的头开始，下一个节点比目标小就向右，否则下降一层，直到第 0 层。
- **高度**：新节点的高度靠抛硬币决定，每高一层的概率是固定的几分之一。平均查找步数是 O(log n)，不需要任何调整来维持平衡。
- **插入**：先像查找一样找到新节点在每一层的前驱，再把自己接进这几层的链表。

Redis 的有序集合也用跳表，理由不同：它执行命令是单线程的，看中的是实现简单、范围操作方便。

### 为什么它适合并发

- 一次插入只改几个前驱节点的 `next` 指针，不分裂、不旋转、不动别的节点。
- 每个指针的修改可以用一次 CAS 完成，不需要锁。
- 插入从第 0 层开始往上接。第 0 层接好的那一刻节点就算存在了；上面几层只是快车道，没接完时查找照样正确，只是慢一点。
- 因此读者在任何时刻看到的每一层都是一条合法的有序链表，不用加锁，也不会被写者挡住。

**CAS**（比较并交换）是一条原子的 CPU 指令：如果某个地址里的值等于预期的旧值，就把它改成新值并返回成功，否则什么都不改并返回失败。用法是"读、算、试着换，失败就重来"。把节点 N 插到 A 与 B 之间：

```
1. N.next = B
2. CAS(&A.next, B, N)
   成功：A → N → B
   失败：别的线程刚在 A 后面插了节点；重新找 N 的前驱，回到第 1 步
```

### 为什么它与 memtable 合拍

无锁结构里最难的是删除节点：要处理别的线程正站在这个节点上的情况。memtable 的删除是插入一条墓碑，节点从不单独移除，整张表刷盘之后一起释放，最难的部分正好用不到。

### 代价

每个节点带若干指针，比 B 树节点费内存；节点散落在内存各处，查找时一路追指针，缓存命中不如把很多 key 放在一个节点里的 B 树。单线程下它未必比平衡树快，优势在多线程。

## 三个具体决定

### 墓碑的表示

| | 空 value 表示删除 | 每条记录带类型标记 |
| --- | --- | --- |
| 格式 | 表、WAL、SST 都只需要 key 与 value | 三处的编码都多一个标记 |
| 空字节串能否当作正常的值 | 不能，`put(k, "")` 与删除无法区分，引擎要拒绝空 value | 能 |
| 增加别的记录类型 | 没有地方放 | 有 |

LevelDB、RocksDB、Pebble 用类型标记：每个内部 key 末尾有 8 字节，高 56 位是序号，低 8 位是类型（写入、删除等）。mini-lsm 用空 value。

本项目采用空 value，与 mini-lsm 的各章格式保持可对照；引擎对外的写入接口拒绝空 value。等 key 需要带上时间戳、本来就要加尾部时，再考虑把类型放进去。

### 查找的三种结果

墓碑使单张 memtable 的查找有三种结果，调用方的处理各不相同：

| 结果 | 含义 | 调用方接下来 |
| --- | --- | --- |
| 没有这个 key 的记录 | 这张表不知道 | 继续查更旧的数据 |
| 有记录，value 为空 | 已被删除 | 停止，报告不存在 |
| 有记录，value 非空 | 找到了 | 停止，返回这个值 |

把第二种当成第一种，更旧的数据里的值就会复活。

### 大小的估算

memtable 不能无限增长：内存有限；它有多大，刷出的 SST 就有多大；它里面的数据只靠 WAL 保护，越大则崩溃后要重放的日志越长。引擎每次写入之后都要判断是否到了上限，多个线程同时在判断，所以必须便宜。

| | 精确统计有效数据 | 粗略累加 |
| --- | --- | --- |
| 做法 | 覆盖写时减去旧 value 的大小 | 每次写入加上 key 长度与 value 长度，覆盖写照加 |
| 并发下的难度 | "换掉旧值"与"取得旧值的大小"要是同一个原子动作 | 一次原子加法 |
| 偏差 | 仍不等于真实内存占用（节点开销、未释放的旧值） | 同一批 key 反复覆盖时偏大，提前冻结，SST 偏小 |

上限是一条"差不多该换了"的软线，不需要精确，采用粗略累加。LSM 面向写入多的场景，不值得为这个数字拖慢每一次写入。LevelDB 统计的是为 memtable 分配的内存总量；它的每次写入带有不同的序号、都是一个新节点，所以同样不扣除被覆盖的旧值。

### 数据怎样交给调用方

有垃圾回收的语言里可以直接返回一个指向节点内存的切片，只要还有人引用，内存就不会释放。Rust 没有垃圾回收，而 memtable 会被冻结、刷盘、然后整张表释放，这些可能发生在别的线程里。必须明确调用方手里的字节归谁管、能活多久。

| | 拷贝 | 借用 | 共享所有权加引用计数 |
| --- | --- | --- | --- |
| 返回类型 | `Vec<u8>` | `&[u8]` | `Bytes` |
| 读的开销 | 一次分配加拷贝 | 无 | 一次原子加一，丢弃时原子减一 |
| 对调用方的约束 | 无 | 引用存活期间 memtable 不能释放，约束沿调用链一路传上去；数据还可能来自 SST 的数据块，同一个返回类型难以表达两种来源 | 无 |
| 内存何时释放 | 调用方丢弃时 | 随 memtable | 最后一个持有者丢弃时；表已释放但值还被人拿着时，那块内存仍占着 |

采用引用计数：`bytes::Bytes` 是一块带计数的字节缓冲，克隆它只增加计数，不拷贝数据。

写入方向相反：`put` 收到的 `&[u8]` 指向调用方的缓冲区，那块内存不归 memtable 管，所以数据进表时必须拷贝一次。这次拷贝省不掉。

工业对照：LevelDB 的 `Get` 把值拷贝进调用方给的字符串；RocksDB 提供 `PinnableSlice`，让调用方钉住数据所在的内存以避免拷贝；Pebble 的 `Get` 返回一个切片和一个 `Closer`，切片在调用 `Close` 之前有效。后两者是借用加显式归还。

## 本项目的做法

`MemTable` 有两个字段：一张 `crossbeam_skiplist::SkipMap<Bytes, Bytes>`，一个 `AtomicUsize` 记估算的大小。跳表不自己实现。

```rust
pub fn put(&self, key: &[u8], value: &[u8])
pub fn get(&self, key: &[u8]) -> Option<Bytes>
pub fn approximate_size(&self) -> usize
```

**`put` 的接收者是 `&self` 而不是 `&mut self`。** Rust 里 `&mut` 的含义是独占：同一时刻只能有一个。多个线程要同时写入，它们手里只能是共享引用 `&self`，修改由内部的并发结构自己保证安全。跳表的 `insert` 和原子计数器的 `fetch_add` 都只需要 `&self`。这类"通过共享引用修改"的类型见 [[rust-learning/notes/09-concurrency/12-原子类型与-compare_exchange|原子类型]]与 [[rust-learning/notes/09-concurrency/03-Send-与-Sync|Send 与 Sync]]。

`get` 的返回值 `Option<Bytes>` 对应查找的三种结果：`None`、`Some(空)`、`Some(非空)`。memtable 自己不解释墓碑，原样交给上一层。

计数器用 `Relaxed`：它与表的内容之间没有需要同时成立的关系，只要每次加法不丢。

## GreptimeDB 的 memtable

GreptimeDB 的存储引擎 mito2 里，memtable 是一个 trait（[memtable.rs](../../references/greptimedb/src/mito2/src/memtable.rs) 的 `Memtable`），有几种实现。与这里相同的地方：写入方法的接收者是 `&self`，trait 要求 `Send + Sync`，表以 `Arc<dyn Memtable>` 的形式被多处共享。

不同的地方来自它是时序数据库。以 [time_series.rs](../../references/greptimedb/src/mito2/src/memtable/time_series.rs) 的实现为例：

| | 本项目 | mito2 的时序 memtable |
| --- | --- | --- |
| 结构 | 一张跳表，key 到 value | 两层：外层是一把读写锁保护的 `BTreeMap`，从时间线的主键到 `Series`；每个 `Series` 各有一把读写锁，里面按列存放这条时间线上的点 |
| 一次写入 | 无锁插入一个节点 | 外层拿读锁找到时间线，再拿这条时间线的写锁追加一个点；只有出现新的时间线时才拿外层的写锁 |
| 删除 | 空 value | 每个点带操作类型与序号，属于类型标记的做法 |

它用的正是"锁加平衡树"，却不受上一节那种排队的拖累，原因在数据的形状：时间线的数量相对固定，绝大多数写入是往已有的时间线上追加，外层的锁几乎总是读锁；真正的修改分散在各条时间线自己的锁上。选什么结构取决于写入落在哪里。

## 引擎里的 memtable

### 为什么要有"冻结"这个状态

memtable 满了要写成 SST。停下写入、把表写成文件、清空再继续，有两个问题：写文件要几十到几百毫秒，其间所有写入都得等；正在被写入的表没有固定的内容，无法写成一个有序的文件。

所以把换表与落盘拆开：满了的表立刻变成只读，同时换上一张新的空表接收写入，这只是换一个指针；只读的那张在后台写成文件，写完再丢弃。只读而尚未落盘的表就是冻结的 memtable，它必须留在内存里，因为其中的数据还没有别处可查。落盘比写入慢时它们会排成一队。

```
引擎状态
├── 可写的 memtable：恰好一张
└── 冻结的 memtable：零张或多张，新的在前
```

点查先查可写的，再从新到旧查冻结的，碰到值或墓碑就停。

### 并发下的三个问题

| 问题 | 经过 | 后果 |
| --- | --- | --- |
| 写入落进已冻结的表 | 写线程读到"当前表是 M1"，此时 M1 被冻结并换成 M2，写线程仍往 M1 插入 | M1 若正被写成 SST，这条记录可能不在文件里，随 M1 丢弃而丢失 |
| 读取漏掉一张表 | 读线程先读到空的冻结列表，此时 M1 被移进冻结列表，读线程再读到当前表是 M2 | M1 被整个跳过，存在的 key 读不到 |
| 重复冻结 | 两个写线程都发现 M1 满了，先后各冻结一次 | 第二次冻结的是刚换上的、几乎为空的表 |

### 两把锁

```
state        读写锁，保护一个指针，指向当前的引擎状态；状态本身不可变
state_lock   互斥锁，让改变结构的操作排队

写入:  拿 state 读锁 → 往当前表插入 → 放锁
       表到了上限：拿 state_lock → 重新检查 → 仍然满才冻结
冻结:  （已持有 state_lock）准备一张新表
       拿 state 写锁 → 复制状态，旧表移进冻结列表，换上新表，切换指针 → 放锁
点查:  拿 state 读锁 → 复制指针 → 放锁；在手里这份状态上从新到旧查
```

- **写入拿的是读锁。** 这把锁保护的是"当前是哪张表"，不是表里的内容；写入只是读这个指针，表本身的并发由跳表负责。冻结拿写锁，意味着此刻没有写入正在进行，第一个问题被挡住。
- **状态是一整份不可变的快照。** 当前表与冻结列表放在同一份状态里，读者一次取走，看到的两样东西必然来自同一时刻，第二个问题被挡住。若给两样东西各配一把锁，读者只能先后去取，各把锁都没有被破坏，取到的却是两个时刻的东西；要修就得两把同时拿，而总是一起拿的两把锁就是一把。
- **读者不长时间持锁。** 读者只在复制指针的一瞬间持读锁，之后在快照上查找。以后点查还要读磁盘，持锁查找会让冻结一直拿不到写锁。旧状态及其引用的表由引用计数保活，最后一个读者放手时才释放。
- **`state_lock` 之后要重新检查。** 排队期间别的线程可能已经冻结过，当初"表满了"的判断已经过期。先在锁外检查，拿到锁后再确认，第三个问题被挡住。

Rust 里锁、守卫与 `Arc` 的用法见 [[rust-learning/notes/09-concurrency/05-Mutex-与锁守卫|Mutex 与锁守卫]]、[[rust-learning/notes/09-concurrency/06-RwLock-与读写访问|RwLock 与读写访问]]、[[rust-learning/notes/09-concurrency/04-Arc：跨线程共享所有权|Arc]]。

为什么不直接在写锁里检查并冻结：以后准备一张新表包含创建 WAL 文件，是磁盘操作。放在写锁里，这几毫秒所有读写都停住；放在 `state_lock` 里只挡住别的结构变更，写锁只在最后切换指针时持有。

### 重复冻结能不能用 CAS 解决

可以。把状态指针做成可原子替换的：读出当前状态，准备好新状态，比较并交换；失败说明别人已经改过，放弃即可。互斥锁加重新检查是悲观的写法，CAS 是乐观的写法，解决的是同一件事。这里仍用互斥锁，理由有三：

- CAS 要先把新状态准备好才能尝试，输的一方白做了准备；以后准备工作包含创建文件，代价不小。
- flush 与 compaction 完成时要先写一条 MANIFEST 记录、再切换状态，而且状态变更的先后必须与 MANIFEST 中记录的先后一致。这是带磁盘操作的两步，CAS 只能保证最后切换的那一下，所以这把锁迟早要有。
- 冻结很少发生，抢锁的开销可以忽略。

即使改用 CAS，第一个问题仍要靠读写锁，或者换一种机制：每张 memtable 带一个"正在写入的人数"的计数，落盘等它归零才开始，Pebble 采用这种做法。

### 工业对照：mini-lsm 与 GreptimeDB

mini-lsm 的结构与上面相同：`state: Arc<RwLock<Arc<LsmStorageState>>>` 加 `state_lock: Mutex<()>`（[lsm_storage.rs](../../references/mini-lsm/mini-lsm/src/lsm_storage.rs)）。

mito2 的状态同样是"读写锁保护一个指向不可变版本的指针"（[region/version.rs](../../references/greptimedb/src/mito2/src/region/version.rs)）：`VersionControl` 里是 `RwLock<VersionControlData>`，其中的 `version` 是 `Arc<Version>`；`Version` 包含 memtable、SST 等，memtable 部分是 [MemtableVersion](../../references/greptimedb/src/mito2/src/memtable/version.rs)，由一张 `mutable` 和一个 `immutables` 列表组成。读者调用 `current()`，持读锁复制一份后放锁。[freeze_mutable](../../references/greptimedb/src/mito2/src/region/version.rs#L99-L121) 读出当前版本，构造换好表的新版本，最后拿写锁换上去。

差别在重复冻结怎样避免。mito2 没有相当于 `state_lock` 的锁，`freeze_mutable` 里也没有重新检查，因为它在更上一层排除了并发：每个 region 绑定到一个固定的工作线程，对这个 region 的写入、冻结、flush 的调度都由这一个线程依次处理（[worker.rs](../../references/greptimedb/src/mito2/src/worker.rs)；冻结由 [flush.rs](../../references/greptimedb/src/mito2/src/flush.rs#L1240) 中的调度器调用，调度器只能被独占访问）。结构变更天然串行，不需要锁。

| | 本项目与 mini-lsm | mito2 |
| --- | --- | --- |
| 状态 | 读写锁加不可变快照 | 相同 |
| 谁能改变结构 | 任何写线程，靠互斥锁排队 | 只有这个 region 的工作线程 |
| 写入怎样到达 memtable | 调用方线程直接写 | 请求发给工作线程，由它写 |

把并发收拢到"每个分区一个线程"是分布式存储里常见的做法，TiKV 的 region 也是如此。

### 导读：mito2 的冻结

GreptimeDB 的代码量很大（mito2 一个引擎就有十五万行），异步、泛型、列式数据、错误处理与指标统计交织在一起，直接通读很难。读它的办法是每次只看与自己刚实现的功能对应的一小段，并且知道哪些行可以先跳过。

下面这段是 [region/version.rs](../../references/greptimedb/src/mito2/src/region/version.rs#L98-L121) 中的冻结，与本项目的 `force_freeze_memtable` 做的是同一件事：

```rust
/// Returns current copy of data.
pub(crate) fn current(&self) -> VersionControlData {
    self.data.read().unwrap().clone()
}

/// Freezes the mutable memtable if it is not empty.
pub(crate) fn freeze_mutable(&self) -> Result<()> {
    let version = self.current().version;
    let time_window = version.compaction_time_window;

    let Some(new_memtables) = version
        .memtables
        .freeze_mutable(&version.metadata, time_window)?
    else {
        return Ok(());
    };

    // Create a new version with memtable switched.
    let new_version = Arc::new(
        VersionBuilder::from_version(version)
            .memtables(new_memtables)
            .build(),
    );

    let mut version_data = self.data.write().unwrap();
    version_data.version = new_version;

    Ok(())
}
```

| mito2 | 本项目 | 说明 |
| --- | --- | --- |
| `self.data.read().unwrap().clone()` | `snapshot()` | 拿读锁，复制一份，放锁 |
| `version.memtables.freeze_mutable(…)` | 复制状态、旧表移进冻结列表、换上新表 | 得到换好表的新 memtable 集合；返回 `None` 表示可写表是空的，不必冻结 |
| `let Some(x) = … else { return … };` | — | 是 `Some` 就取出里面的值继续，否则走 `else` 提前返回 |
| 行尾的 `?` | — | 出错就把错误直接返回给调用方 |
| `VersionBuilder::from_version(version).memtables(…).build()` | `guard.as_ref().clone()` 之后改字段 | 以旧版本为底、只替换 memtable 部分，造出新版本 |
| `Arc::new(…)` | `Arc::new(new_state)` | 新版本包进 `Arc` |
| `self.data.write().unwrap()` 后给 `version` 赋值 | `*guard = Arc::new(new_state)` | 拿写锁，把指针换成新版本 |

可以先跳过的：`time_window`（按时间分区，时序引擎特有）、`metadata`（表结构）。

不同之处有一个：这里没有 `state_lock`，新版本在拿写锁之前就基于旧版本造好了，也没有重新检查。它依靠的是每个 region 只由一个工作线程处理，冻结不会并发发生。

## 基准对比：无锁跳表与一把锁加平衡树

同一份负载（100 万条、key 16 字节、value 100 字节），吞吐单位是百万次操作每秒，取三次运行的中位数。完整数据与条件见 [结果记录](../bench/results/2026-10-08-memtable-vs-btreemap.md)。

| 线程 | 结构 | 随机写入 | 点查（key 存在） | 写入的 p99 |
| ---: | --- | ---: | ---: | --- |
| 1 | 互斥锁加 `BTreeMap` | 3.10 | 2.24 | 约 1 微秒 |
| 1 | 跳表 | 1.43 | 0.92 | 约 2 微秒 |
| 4 | 互斥锁加 `BTreeMap` | 1.04 | 0.67 | 约 36 微秒 |
| 4 | 跳表 | 3.31 | 3.00 | 约 3 微秒 |
| 8 | 互斥锁加 `BTreeMap` | 0.87 | 0.64 | 约 88 微秒 |
| 8 | 跳表 | 5.16 | 5.01 | 约 4 微秒 |

- 单线程下跳表只有平衡树的三分之一到一半，这是它的代价。
- 一把锁的方案线程越多越慢：线程都在排队等锁，吞吐下降，尾延迟涨了两个数量级。
- 跳表随线程数增长，尾延迟基本不变。两者在 2 个线程附近交叉。

选跳表换来的不是"更快"，而是"多个线程一起写时不互相挡住"。

## 与 B+Tree 的对应

| CoW B+Tree | memtable |
| --- | --- |
| 每个事务持读锁，关闭取写锁等所有事务结束 | 每次写入持状态的读锁，冻结取写锁等所有写入结束 |
| 映射列表是原子指针指向的不可变列表，扩容时复制后切换 | 引擎状态是读写锁保护的指针指向的不可变快照，冻结时复制后切换 |
| 事务内的内存节点，提交时一次编码成页（[原子写批次](../../storage/notes/05-storage-recovery/06-atomic-write-batches.md)） | 跨越很多次写入的内存表，写满后一次编码成 SST |
| 单写者；读者读旧页，不与写者碰同一块内存 | 多写者；读者与写者在同一个结构上 |
| 删除从页里移除记录 | 删除是插入墓碑，表只增不减 |
| 读者拿到的是页的借用视图，事务结束后失效 | 读者拿到带引用计数的缓冲，不受表的生命周期约束 |

## 常见错误

- **把墓碑当作"不存在"返回。** 上层会继续查更旧的数据，被删除的值复活。
- **覆盖写时没有替换旧记录。** 跳表有"已存在就不插入"的接口，用错了后写的值不生效。
- **用"读出、加、写回"三步更新大小。** 两个线程交错时会丢掉其中一次，要用一次原子加法。
- **在拿到 `state_lock` 之前做重新检查。** 检查发生在锁外，等拿到锁时结论可能已经过期，与没有检查一样，几乎为空的表仍会被冻结。检查必须在持锁期间做。
- **冻结时原地修改当前状态。** 读者的快照与锁里的指针指向同一份状态，原地修改会让读者的快照在读的过程中变化。在 Rust 里这一步过不了编译：通过 `Arc` 只能得到只读访问。要复制一份、改副本、再换指针。
- **把冻结的表追加到列表末尾。** 列表约定新的在前，点查从前往后找；顺序反了，较旧的表里的值会盖住较新的。
- **持着状态的读锁去冻结。** 冻结要拿同一把锁的写锁，会一直等自己放开读锁，形成死锁。写入完成、放开读锁之后再判断是否冻结。
- **给已经能并发的结构再套一把锁。** 跳表的插入与查找只需要共享访问，外面再加互斥锁，所有线程又变成排队。实测 8 个线程时吞吐只有不加锁时的十分之一左右，比"锁加平衡树"还慢。判断的依据是方法的接收者：只要 `&self` 就能调用的，本身已经允许多个线程同时调用。
